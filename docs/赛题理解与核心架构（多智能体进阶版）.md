## 核心架构：这个系统的“大脑集群”是怎么工作的？
在进入具体实例前，先建立一个基于 **LangGraph** 理念的多智能体协作模型 (Multi-Agent System)。

### 1. 感知与交互层 (Interface & Memory)
+ 接收用户语音/文本。
+ **【核心升级】思维链可视化 (Thinking Stream)**：在前端实时展示“正在路由...”、“正在反问确认...”、“正在查询物化视图...”，消除用户等待焦虑。
+ 读取 Session 历史对话，维持多轮交互上下文。

### 2. 路由决策层 (Router Agent / Front-Desk) —— 带“反问”能力的智能前台
+ **前台接待与意图识别 (Intent Recognition)**：
    - **澄清机制 (Clarification Loop)**：设置意图置信度阈值（= 0.7）。若意图模糊（置信度 < 0.7），拦截分发并触发反问，直到用户补充关键信息，有效避免 Agent 产生幻觉。
+ **死循环熔断 (Circuit Breaker) —— 【企业级风控】**：
    - 在复杂任务中，设置 `max_hops = 5`。一旦流转超过 5 次仍未解决，Router 强制接管并输出“任务过于复杂，需人工介入”，触发 Human-in-the-loop。

### 3. 专家执行层 (Expert Agents via MCP)
+ **数据分析 Agent (Data Analyst)**：
    - **权限控制**：通过 MCP 挂载 Read-Only 数据库权限。
    - **能力**：负责 Text-to-SQL（精准路由至 `daily_energy_summary` 物化视图）、Python 复杂计算（COP）。内置 Self-Correction。
+ **故障诊断 Agent (Diagnose Expert)**：
    - **混合检索**：挂载 RAG 工具，支持设备 ID 过滤 + Vector 语义描述的混合检索，精准定位故障手册。
    - **逻辑推理**：结合 `energy_data` 实时异常状态与知识库进行归因分析。

### 4. 表达与控制层 (Presentation & Safety)
+ 将枯燥的 JSON 数据转化为自然语言。
+ **可解释性注入**：在回答中附带**“数据来源”**（我是基于哪张表、哪条手册得出的结论）。
+ **人机协同**：遇到高危操作（如“派发工单”）触发 Human-in-the-loop 机制，弹出交互卡片。

## 场景一：多轮对话中的“模糊意图澄清与上下文继承” (难度：⭐⭐⭐)
**用户第一句（模糊指令）：** “我看那个好像有点问题。”

1. **Router Agent 思考 (Ambiguity Check)**：
    - 分析：指代词“那个”不明。判定：`Intention=Unknown`, `Confidence=0.3`。
    - **决策**：触发 `Clarification Loop`，不分发。
2. **Router Agent 回复（反问）：** “您是指**能耗数据**有异常，还是**特定设备**出现了报警？”

**用户第二句（补充信息）：** “是图书馆昨天的电费，太高了。”

1. **Router Agent 思考**：
    - 提取实体：`Location="Library"`, `Time="Yesterday"`, `Metric="Cost/Electricity"`.
    - 判定：`Intention=Data_Query`, `Confidence=0.95`。分发给 **Data Analyst Agent**。
2. **前端 UI 变化**：显示 `[系统] 意图已确认，正在接入数据分析师...`
3. **Data Analyst 执行**：调用 MCP `query_energy_metrics`。返回结果 `1520.5 kWh`。
4. **Agent 最终回复**：汇报电量与电费。

**用户第三句（上下文继承）：** “那空调系统呢？”

1. **Router Agent 补全上下文**：从 Session 记忆提取并补全为：查询 “Library” + “Yesterday” 的 “hvac” 数据。
2. **Data Analyst 执行**：再次调用工具查出数据。展示了从“模糊”到“清晰”再到“省略”的完整控制能力。

## 场景二：复杂计算与统计分析 (难度：⭐⭐⭐)
**用户提问：** “计算一下教学楼上个月的制冷能效比（COP），并判断是否正常。”

1. **Data Analyst 思考**：这是一个复杂计算，大模型自己做除法容易错，必须调用封装好的 MCP 统计工具。
2. **MCP 工具调用**：调用 `calculate_system_cop(building_id="Education", month="2023-09")`。
3. **后端代码执行**：从 `energy_data` 查总制冷量和空调耗电。物理异常捕获防除零。基准比对。
4. **Agent 回复**：给出 COP 值，报告是否低于基准，并渲染趋势折线图。

## 场景三：混合编排与人机协同闭环 (故障诊断+知识库+工单生成) (难度：⭐⭐⭐⭐⭐ - 满分杀手锏)
**用户提问：** “办公楼今天凌晨3点的数据是不是有问题？帮我处理一下。”

_此场景展示了 Data Agent 与 Diagnose Agent 的接力协作，以及底层数据库字段的真实映射。_

**步骤 1：事实核查 (Fact Checking via Data Analyst)**

+ **Agent 状态**： `Data Analyst 正在运行...`
+ **动作**：调用工具检索该时段数据 `query_energy_metrics(building_id="Office", time="03:00")`。
+ **Result (真实字段映射)**： `{"meter_device_id": "M-OFF-001", "electricity_kwh": 450, "operation_status": "Anomaly"}`。
+ **中间结论**：数据库 `operation_status` 枚举字段已标记为 Anomaly，确认设备 M-OFF-001 存在异常高耗电。

**步骤 2：关联分析 (Correlation via Data Analyst)**

+ **动作**：查询同一时间段的环境与人员传感数据。
+ **Result**： `{"occupancy_density_per_100sqm": 0, "ambient_temp_c": 15.0}` (此时楼内完全无人，且室外温度极低)。
+ **推理**：人员密度为0 + 低温 + 高耗电 = 典型的策略配置失误（空转）。任务移交给 Diagnose Agent。

**步骤 3：混合检索 (Hybrid RAG via Diagnose Agent)**

+ **动作**：调用 MCP `rag_search`。
    - _Query_: "zero occupancy high electricity_kwh"
    - _Metadata Filter_: `{"device_id": "M-OFF-001"}` (利用设备ID精准过滤关联手册)
+ **RAG 检索结果**：提取出：“若夜间监控人员密度（occupancy_density）归零，但系统未进入休眠，需检查定时器继电器。”

**步骤 4：可解释性回复与人工授权 (Human-in-the-loop)**

+ **Agent 最终回复**：

> “**诊断结论**：经核查，凌晨 3 点办公楼人员密度为 0 (`occupancy_density_per_100sqm=0`)，但设备 `M-OFF-001` 耗电量激增，系统状态已标记为 `Anomaly`。  
**原因分析**：结合《运维手册》，极可能是定时策略失效导致的无效空转。  
**建议操作**：我已为您生成维修工单，建议重置该设备的定时控制器。”
>

+ **生成式 UI (Generative UI)**：
    - 前端直接弹出一个 **【 ****🛠️**** 维修工单卡片 】**。包含设备 ID、优先级、建议动作。
    - **用户操作**：点击 `[ 立即派单 (需确认) ]`。
    - **系统反馈**：按钮变绿，弹出 Toast：“工单已推送到运维班组。” (闭环完成)

## 后续演进规划 (Future Extension)：构建可信 AI 审计体系
现阶段，我们将 AI 智能体的推理轨迹（Trace）和数据引用的上下文轻量级地保存在应用层内存（LangGraph State）中，以供前端渲染。在系统的 **Phase 2（后续企业级演进）** 中，我们将构建持久化的 **AI 决策审计模块**，以打破“黑盒”，建立工业级信任。

**规划的审计数据蓝图（对应 AI 决策审计表结构）：**  
未来我们将实现独立部署的审计日志库，包含以下核心数据追踪：

1. **全链路追踪 (Traceability)**：记录每一次调用的 `trace_id`、使用的 `raw_prompt` 和原始调用链。
2. **数据溯源 (Data Lineage)**：精准关联每一次结论对应的 `energy_data` 记录 ID 与手册分片 ID，确保“有据可查”。
3. **效能监控 (LLM FinOps)**：统计 `execution_time` 和 `token_usage`，进行持续的性能优化与成本核算。
4. **人类反馈闭环 (RLHF)**：记录 `human_feedback`，为后续模型的微调（Fine-tuning）积累高质量的业务对话数据。
