## 3. 已完成的核心结果

本轮改造后，系统已经从“AI 批准即已派单”的演示逻辑，升级为“AI 审批 -> 待派工 -> 选择候选人 -> 派工 -> 接单/到场/开工”的真实主链路。

当前已经具备以下核心能力：

1. AI 审批通过后，工单会先进入 `pending_dispatch`，不再直接等于 `dispatched`
2. 管理端可以查看派工候选人并完成手动派工
3. 候选人推荐不再只按“在手工单少”排序，而是结合技能、班组、值班状态、楼宇覆盖、负载上限综合计算
4. 维修端可以按真实执行动作推进：接单、到场、开始处理
5. 维修人员已经具备基础画像：班组、技能、值班状态、派工开关、覆盖楼宇、负载上限
6. 移动端管理页和维修页已经可以消费这些新增能力并展示出来

## 9. 当前系统相对改造前的提升

本轮改造带来的核心提升如下：

### 9.1 业务语义更清晰

之前：

- AI 批准 ≈ 已派单

现在：

- AI 审批通过 -> `pending_dispatch`
- 调度人员选择候选人 -> `dispatched`
- 维修人员动作推进 -> `accepted / arrived / processing`

### 9.2 管理端派工决策更可信

之前：

- 只能看到一个简单候选列表
- 无法解释为什么推荐某人

现在：

- 能看到班组、技能、楼宇覆盖、值班、负载、推荐理由

### 9.3 维修端页面与后端语义开始对齐

之前：

- UI 有很多执行状态，但后端缺少真实动作

现在：

- 接单、到场、开始处理均由明确接口和真实时间字段驱动

### 9.4 后续扩展空间明显变大

当前结构已经为以下方向打下基础：

- 改派
- 转派
- 拒单
- 协同支援
- 自动派工
- 班组调度

## 10. 当前仍未完成的部分

以下内容尚未完成，属于下一阶段工作：

### 10.1 `dispatch_tasks` 独立执行对象尚未引入

当前仍是“在 `work_orders` 上承载最小派工执行语义”，尚未进入完整执行层建模。

因此暂时还不支持：

- 多次派工尝试
- 改派历史链路
- 拒单后重派
- 协同班组子任务

### 10.2 Web 端旧工单页尚未完成语义重构

当前移动端已完成第一、二阶段主要落地，但桌面 Web 的工单页仍沿用旧状态语义，尚未按新的待派工和派工推荐逻辑完整重构。

### 10.3 数据库迁移需要在实际环境执行

代码、测试和构建已经完成，但若要在线上或本地真实数据库生效，仍需要执行：

- `017_work_order_dispatch_phase1.sql`
- `018_worker_dispatch_profiles.sql`

### 10.4 构建 warning 仍存在

移动端 H5 构建虽已通过，但仍存在仓库内原有问题：

- `Noto Sans SC` 字体资源解析 warning
- Sass legacy API / `@import` deprecation warning

这些 warning 不影响本次功能上线验证，但后续可以单独清理。

## 12. 总结

截至当前，本项目在派单系统与维修端方面，已经完成了从“审批驱动演示闭环”向“可解释、可调度、可执行”的第一轮真实业务化升级。

> **系统已经不再只是“AI 批准后把单丢出去”，而是开始具备“知道什么时候该派、该派给谁、为什么派给他、维修现在处理到哪一步”的基础能力。**

这意味着：

- 主链路已经跑通
- 人员画像已经建起来
- 派工推荐已经具备解释性
- 维修端执行流程已经开始真实化

下一步的重点，不再是“有没有派单功能”，而是进入更完整的执行域建设：`dispatch_tasks`、改派、协同、拒单与自动派工。
