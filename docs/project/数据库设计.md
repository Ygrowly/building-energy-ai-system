## 二、数据库设计
本章重点：本章围绕系统设计所对应的数据底座展开，重点说明平台如何将建筑主数据、能耗时序数据、分析预警结果、工单派工闭环数据以及智能交互与知识沉淀数据统一组织到同一套数据库体系中。章节内容不仅解释表结构如何服务于查询统计、异常检测、预测预警、工单流转和经验回流，也强调数据库分层、关键关系、数据血缘以及索引性能设计如何共同支撑赛题要求和现有项目实现，确保系统具备可查询、可分析、可追溯、可扩展的工程能力。

### 2.1 数据库设计原则
数据库设计并不是孤立的存储设计，而是为赛题要求中的“数据构建、查询统计、智能运维和系统集成”提供结构支撑。当前数据库设计遵循以下原则：

1. 主数据与时序事实分离，避免楼宇、设备等静态元数据与高频采样数据混杂。
2. 原始数据、聚合数据、预警数据和业务闭环数据分层组织，便于查询和追溯。
3. 智能分析所需的期望值、症状标记、异常事件和预测事件单独建模，避免直接写死在原始表中。
4. 工单、派工、审批、共享调度和经验回流采用独立业务表承载，保证状态可审计。
5. AI 会话、知识文档、维修经验单独沉淀，保证后续问答与复用能力可持续演进。

总体上，当前项目采用 PostgreSQL 作为核心结构化数据库，Redis 作为缓存和通知通道，RAGFlow 作为文档知识检索引擎。这样的组合既能够保证结构化业务逻辑的完整性，也能支撑智能问答和运维闭环所需的知识增强能力。

### 2.2 数据库逻辑分层设计
从数据库逻辑看，项目并没有把所有内容揉进一个“大宽表”，而是按主数据层、时序事实层、分析预警层、业务闭环层和智能交互沉淀层进行组织。

| 层次 | 核心表 | 职责 |
| --- | --- | --- |
| 主数据层 | `buildings`、`devices`、`users`、`worker_teams`、`worker_profiles`、`worker_skills` | 维护楼宇、设备、用户、班组和人员画像等稳定实体 |
| 时序事实层 | `energy_data`、`daily_energy_summary`、`device_telemetry_hourly`、`device_status_latest` | 存储小时级能耗明细、日级聚合和设备状态事实 |
| 分析预警层 | `kpi_expected_hourly`、`kpi_anomaly_flags`、`anomaly_events`、`predicted_anomaly_events`、`anomaly_incidents` | 承载基线、症状、中间检测结果、异常与预测事件 |
| 业务闭环层 | `work_orders`、`dispatch_tasks`、`dispatch_events`、`dispatch_hall_entries`、`dispatch_hall_applications`、`context_events`、`work_order_audit_log`、`work_order_anomaly_links` | 承载审批、派工、执行、协同、审计与证据关联 |
| 智能交互沉淀层 | `dataset_files`、`chat_sessions`、`ai_assistant_sessions`、`ai_assistant_messages`、`worker_ai_step_plans`、`worker_ai_step_events`、`maintenance_experiences`、`maintenance_experience_usage_logs`、`maintenance_experience_feedback` | 承载数据集管理、AI 对话、步骤计划、维修经验与反馈 |


这一分层意味着系统可以同时支撑三类核心问题：

+ 数据问题：某楼某时段指标表现如何。
+ 业务问题：当前有哪些异常、工单、派工和超时事项。
+ 智能问题：类似问题以前怎么处理、当前 AI 会话上下文是什么、知识库有没有可引用内容。

### 2.3 主数据层设计
主数据层为全系统提供稳定实体与外键来源，是所有分析和业务数据的锚点。

#### 2.3.1 `buildings`
`buildings` 是楼宇主数据表，核心字段包括 `building_id`、`primary_space_usage`、`sqm` 和 `timezone`。  
它负责定义楼宇身份、用途类别、面积口径和时区口径，为后续能耗强度计算、按用途分析和本地时间换算提供基础。

#### 2.3.2 `devices`
`devices` 负责挂载楼宇下的计量设备与传感器，核心字段包括 `device_id`、`building_id` 和 `device_type`。  
系统当前默认围绕电表、水表、HVAC、环境传感器等基础设备类型组织设备语义。

#### 2.3.3 `users` 与维修画像表
`users` 负责系统登录主体；`worker_teams`、`worker_profiles`、`worker_profile_skills` 等表负责描述维修人员的班组、服务楼宇、技能标签和可处理范围。这一层直接服务于智能派单评分与共享调度大厅目标匹配。

### 2.4 时序事实层设计
时序事实层是系统分析能力的基础。

#### 2.4.1 `energy_data`
`energy_data` 是全系统最核心的事实表，采用复合主键 `(timestamp, building_id)`。  
核心字段包括：

+ `electricity_kwh`
+ `water_m3`
+ `hac_energy`
+ `sim_supply_temp_c`
+ `sim_return_temp_c`
+ `air_temp_c`
+ `dew_temp_c`
+ `humidity_rh_pct`

为避免字段缩写带来的理解歧义，这里补充各字段的业务含义：

| 字段 | 含义 | 单位 | 备注 |
| --- | --- | --- | --- |
| `electricity_kwh` | 当前监测时段的建筑总电耗 | kWh | 用于能耗统计、趋势分析和异常检测 |
| `water_m3` | 当前监测时段的建筑总用水量 | m3 | 用于水耗统计和漏损异常分析 |
| `hac_energy` | 暖通空调综合能耗 | kWh | 字段名沿用现有数据与代码命名，可理解为 HVAC 能耗 |
| `sim_supply_temp_c` | 模拟供水温度 | ℃ | 常用于与回水温度共同计算温差和效率代理指标 |
| `sim_return_temp_c` | 模拟回水温度 | ℃ | 与供水温度配合用于工况分析 |
| `air_temp_c` | 环境空气温度 | ℃ | 作为环境侧特征参与基线、异常和预测分析 |
| `dew_temp_c` | 露点温度 | ℃ | 反映空气含湿状态，可辅助判断环境工况 |
| `humidity_rh_pct` | 相对湿度 | % | 反映环境湿度水平 |

该表直接承接赛题要求中的建筑编号、监测时间、电耗、水耗、空调系统能耗、供回水温度、环境温湿度等关键字段，是多条件查询、COP 计算、异常分析和预测特征构造的基础数据源。

#### 2.4.2 `daily_energy_summary`
`daily_energy_summary` 是围绕 `energy_data` 构建的物化视图，主要承接日级聚合查询。  
之所以单独设置这一层，是因为首页总览、趋势图和报表导出对日级统计有高频访问需求，如果每次都直接对原始明细表做聚合，响应速度和数据库压力都会受到影响。

#### 2.4.3 设备事实表
`device_telemetry_hourly` 用于保留设备历史遥测；`device_status_latest` 用于保留设备当前快照。  
前者适合做趋势分析与故障回溯，后者适合做设备列表与即时状态展示。两者搭配可以避免前端每次都扫描全部历史记录。

### 2.5 分析预警层设计
分析预警层连接“原始数据”与“运维动作”，是赛题中“智能分析”和“智慧运维”的桥梁。

#### 2.5.1 `kpi_expected_hourly`
该表保存逐楼逐小时的期望值基线，包括：

+ `water_m3_expected`
+ `electricity_kwh_expected`
+ `hac_energy_expected`
+ `sim_supply_temp_c_expected`
+ `sim_return_temp_c_expected`
+ `humidity_rh_pct_expected`

它回答的是“在正常工况下，这个时刻应该大致运行到什么水平”，为后续异常识别与预测预警提供参照系。

#### 2.5.2 `kpi_anomaly_flags`
该表保存更细粒度的症状标记，例如：

+ `flag_water`
+ `flag_electricity`
+ `flag_hvac_energy`
+ `flag_supply_deviation`
+ `flag_return_deviation`
+ `anomaly_phase`
+ `hvac_diagnosis`

这意味着系统不是直接把“异常”写成最后结论，而是先保留一层可解释的症状信息，方便后续生成事件、工单和诊断解释。

#### 2.5.3 `anomaly_events` 与 `predicted_anomaly_events`
`anomaly_events` 表示已经发生的异常事件，保存 `rule_triggered`、`actual_value`、`threshold_value`、`expected_value`、`deviation_pct`、`hvac_root_cause` 等字段。  
`predicted_anomaly_events` 表示未来 6/12 小时的预测风险，保存 `as_of_timestamp`、`forecast_for_timestamp`、`metric_name`、`predicted_value`、`risk_level` 等字段。

两张表一张面向“事后处置”，一张面向“事前预警”，共同构成了系统的风险入口层。

### 2.6 业务闭环层设计
业务闭环层回答“异常发现之后系统怎么处理”。

#### 2.6.1 `work_orders`
`work_orders` 是工单主表，记录异常问题从待审批到关闭的完整生命周期。  
除 `status` 外，当前系统还保留：

+ `approval_status`
+ `dispatch_summary_status`
+ `work_result`
+ `ai_decision`
+ `ai_reason`
+ `assigned_to`
+ `pending_dispatch_at`
+ `worker_notes`

这意味着工单并不只是一个单字段状态，而是可拆解为审批维度、执行维度和处理结果维度，便于做更精确的统计和问询。

#### 2.6.2 `dispatch_tasks` 与 `dispatch_events`
`dispatch_tasks` 用于记录每一次真实派工尝试，包括：

+ 派给了谁
+ 第几次尝试
+ 当前派工状态
+ 接单、到场、开始处理、完成等关键时间点
+ 超时与提醒信息

`dispatch_events` 则进一步沉淀派工过程中的动作轨迹，使系统能够回看调度过程而不只是看到最终结果。

#### 2.6.3 共享工单大厅
`dispatch_hall_entries` 和 `dispatch_hall_applications` 用于承接“未指派协同”“超时待接管”“共享接管申请”等复杂调度场景。  
这层设计意味着系统的派工能力不是一对一的单线派发，而是具备共享协同、接管、超时兜底和再分配能力。

#### 2.6.4 `context_events`
`context_events` 保存装修、加班、团建、极端天气、维护窗口等背景事件，是 AI 审批的重要依据。  
它把“纯数值异常”和“业务上下文”连接起来，使审批逻辑不至于沦为只看阈值大小。

#### 2.6.5 `work_order_audit_log`
该表用于保留工单每次状态变化的审计记录，包括动作人、动作类型、前后状态和附加详情。  
它保证系统能解释“为什么这张工单通过了”“为什么这次是自动批准”“为什么被管理员覆盖”。

### 2.7 智能交互与知识沉淀层设计
#### 2.7.1 `dataset_files`
`dataset_files` 负责记录结构化数据文件上传信息，包括文件路径、原始文件名、行列统计、字段摘要和上传人。  
它是“数据接入可回看”的关键，不然系统只能知道数据被导入了，却不知道来源是什么。

#### 2.7.2 `chat_sessions`
`chat_sessions` 用于保存通用 AI 会话元数据，包括：

+ `messages_json`
+ `extra_state_json`
+ `message_count`
+ `last_message`
+ `building_id`

这使得碳小能等对话不是一次性调用，而是可以在同一上下文中继续追问、继续补图表和继续输出 artifact。

#### 2.7.3 AI 助手与维修指导表
围绕运小维和维小修，系统还设计了：

+ `ai_assistant_sessions`
+ `ai_assistant_messages`
+ `worker_ai_step_plans`
+ `worker_ai_step_events`
+ `ai_media_assets`

这些表共同承载移动维修指导、步骤计划、现场对话和图片/语音等多模态辅助信息。

#### 2.7.4 `maintenance_experiences`
`maintenance_experiences` 是经验回流层的核心表。它不只保存一段备注，而是保存：

+ 来源工单、派工和步骤计划
+ 故障类型、设备类型、症状标签
+ 原始描述与整理后的经验文本
+ 建议步骤、安全提示、适用条件
+ 使用次数、反馈评价和向量索引状态

这意味着“经验库”并不是简单的留言板，而是一套可持续积累、可被后续问答和维修指导复用的结构化知识沉淀体系。

### 2.8 关键关系与数据血缘设计
从实体关系上看，系统的主链路可以概括为：

`buildings -> devices -> energy_data -> kpi_expected_hourly / kpi_anomaly_flags -> anomaly_events / predicted_anomaly_events -> work_orders -> dispatch_tasks -> maintenance_experiences`

在此基础上还有三条补充链路：

1. `context_events -> work_orders`：为 AI 审批提供业务上下文。
2. `dispatch_hall_entries -> dispatch_hall_applications`：为复杂调度提供共享协同能力。
3. `chat_sessions / ai_assistant_sessions -> maintenance_experiences`：把 AI 会话和最终经验沉淀连接起来。

这种数据血缘设计的好处是：

+ 从任何一条异常都能追溯到楼宇、设备和原始时序数据。
+ 从任何一张工单都能追溯到异常来源、审批依据和派工过程。
+ 从任何一条维修经验都能回溯到来源工单、来源设备和使用反馈。

### 2.9 索引与性能设计
当前数据库并不追求“表越少越好”，而是追求“在可解释前提下的查询效率与业务可维护性”。  
关键优化主要体现在：

+ `energy_data(building_id, timestamp DESC)`：支持楼宇 + 时间窗口查询。
+ `daily_energy_summary(day, building_id)`：支持日级趋势和报表查询。
+ `anomaly_events`、`predicted_anomaly_events`：按楼宇、时间、未解决状态建立索引。
+ `context_events`：按时间范围和楼宇范围建立索引，支撑审批时快速匹配。
+ `work_order_audit_log`：按工单和时间建索引，支撑审计回溯。
+ `dispatch_hall_entries`、`dispatch_hall_applications`：按状态、创建时间和申请人建立索引，支撑共享大厅处理。
+ `maintenance_experiences`：按建筑、设备类型、故障类型和向量状态建立索引，支撑经验检索与复用。

结合 Redis 缓存后，系统形成了“数据库保证真实一致性、缓存承接高频访问、物化视图承接聚合读”的三层性能策略。

### 2.10 与赛题要求的闭环说明
从赛题视角看，数据库设计最终要回答的不是“有多少张表”，而是“这些表能不能支撑赛题要求的系统能力”。当前答案是肯定的：

+ 数据集构建与标准化：由 `dataset_files`、`energy_data` 承接。
+ 查询统计与图表报表：由 `energy_data`、`daily_energy_summary`、MCP 工具和 artifact 渲染承接。
+ 智慧运维与知识问答：由 `chat_sessions`、RAGFlow、经验表和 AI 助手表承接。
+ 异常、预测、审批、派工、维修闭环：由 `kpi_*`、`anomaly_*`、`work_orders`、`dispatch_*`、`maintenance_experiences` 承接。

因此，当前数据库不是为了“配合页面展示”而设计，而是为了完整支撑一套从数据接入到运维处置再到知识沉淀的建筑能源智能管理闭环而设计。
