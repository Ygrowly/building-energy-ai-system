## 一、系统设计
本章重点：本章围绕赛题提出的“数据接入、查询统计、智能问答、智慧运维、系统集成”五个核心要求，对平台的总体设计思路进行展开说明。重点阐述系统如何在多端接入、统一接口、LangGraph + MCP + RAG 智能分析、AI 审批与智能派工、多端协同和可靠性保障等方面形成完整架构，并说明系统设计如何支撑后续数据库设计和接口设计的落地实现。通过本章可明确本项目不是单一展示页面或单点 AI 能力，而是一套面向建筑能源管理与运维闭环的完整平台方案。

### 1.1 设计背景与总体目标
赛题明确要求围绕“能耗数据构建、查询统计、大模型智慧运维、Web 系统集成”四个方向构建一体化解决方案。从业务角度看，建筑能源管理场景的核心问题并不只是“数据有没有被采集”，而是“数据能不能被规范接入、快速查询、有效解释，并最终驱动运维动作”。如果系统只能展示图表而不能支撑后续处置，那么它更像展示平台，而不是能源智能管理系统。

“绿枢智控”因此将系统目标定义为四个层次：

1. 构建可导入、可核验、可追溯的标准化能耗数据底座。
2. 构建兼顾精确筛选与自然语言交互的查询统计能力，支撑多条件查询、时段汇总、COP 计算、异常分析与报表导出。
3. 构建以异常检测、预测预警、知识问答、AI 审批、智能派单和移动维修为核心的智慧运维链路。
4. 构建从数据接入、分析诊断、工单流转、派工执行到经验沉淀的完整业务闭环，使系统不仅能“看到问题”，还能“推动问题被处理掉”。

从系统定位看，“绿枢智控”不是单一看板，也不是单一聊天机器人，而是一套面向建筑能源场景的智能化运营平台。它既要回答“现在运行得怎么样”，也要回答“为什么会这样”和“接下来应该怎么处理”。因此，系统设计不能只覆盖前端页面或后端接口，而必须同时覆盖数据治理、智能分析、运维执行、知识复用和多端协同五个层面。

### 1.2 与赛题要求的对应关系
为了确保方案不脱离赛题要求，系统设计将功能能力与赛题任务逐项对齐。对应关系如下：

| 赛题要求 | 项目实现 | 对应说明 |
| --- | --- | --- |
| 能耗数据集构建、清洗与标准化 | 数据中心上传、列映射、SSE 导入、`energy_data` 入库 | 支撑不同口径样本的统一接入 |
| 多条件精准查询 | Web 查询统计页、MCP 数据查询工具 | 支撑按建筑、时间、指标、阶段筛选 |
| 时段汇总、COP 计算、异常分析 | 日级聚合、物理规则、COP 代理算法、异常研判 | 对应赛题要求的三类核心分析 |
| 至少 2 种图表展示、自动生成统计报表 | ECharts 图表、artifact 渲染、报表导出 | 支撑趋势图、对比图、指标卡、下载链接 |
| 基于知识库和轻量模型的运维问答 | RAGFlow、RAG 兜底、本地经验库、碳小能/运小维/维小修 | 对应知识问答与运维辅助 |
| 响应能耗查询、设备状态查询、异常原因分析 | MCP 工具 + Diagnose Agent + 工单上下文 | 支撑面向管理者和维修者的差异化回答 |
| 系统集成与全流程顺畅交互 | Web 管理端、移动运维端、移动维修端、统一 `/api` 服务层 | 支撑完整闭环演示 |


用一句话概括，赛题强调的是“数据 + 分析 + 系统 + 智能闭环”，而本项目的系统设计就是沿着这四条主线组织的。

### 1.3 总体架构设计
系统总体采用 B/S 架构与多端协同模式，整体可分为表现层、接口层、智能分析层和数据层四个层次。

| 层次 | 组成 | 主要职责 |
| --- | --- | --- |
| 表现层 | Vue 3 Web 端、Uni-app H5 端 | 提供首页总览、查询统计、数据中心、工单管理、人员画像、移动工作台等功能 |
| 接口层 | FastAPI、JWT、REST API、SSE 流式接口 | 提供认证、数据、分析、工单、派单、AI 会话与通知等统一服务 |
| 智能分析层 | LangGraph、MCP 工具链、RAGFlow、预测服务、异常检测服务、审批与派工策略服务 | 负责自然语言理解、工具调用、知识增强、诊断推理和业务决策辅助 |
| 数据层 | PostgreSQL、Redis、本地缓存、文档知识源、经验沉淀表 | 承载结构化数据、业务闭环数据、缓存数据与知识数据 |


这一架构的设计重点不在于技术栈本身，而在于边界清楚：

+ 前端主要负责交互和展示，不承载复杂业务规则。
+ 后端统一收口所有业务接口与状态流转逻辑。
+ 大模型不直接绕过业务系统写库，而是通过受控工具链和正式接口参与流程。
+ 数据层既服务查询统计，也服务异常、预测、工单与经验复用。

这样设计的直接好处是：数据、智能分析和业务执行三个层面不会互相耦死，后续新增分析规则、扩展表结构或增加新前端入口时，不需要整体推翻现有实现。

### 1.4 查询统计模块设计
查询统计模块是系统面向赛题“查询统计”要求的核心承载部分。该模块并非只有一个页面，而是由“固定页面查询能力 + MCP 工具查询能力 + AI 解释能力”共同组成。

#### 1.4.1 固定页面查询
固定页面查询主要面向需要稳定、可复现、可导出的分析场景。用户可以按建筑、时间范围、指标和异常类型进行筛选，系统通过结构化接口返回能耗趋势、实际值与额定值对比、异常分布、统计汇总等结果。  
这一能力适合日报、周报、对比分析和答辩演示，因为每次输入相同条件都能得到一致输出。

#### 1.4.2 MCP 工具查询
当用户并不清楚应该点哪一个页面、选哪一组条件时，系统通过 MCP 工具链提供自然语言查询能力。当前项目内已落地的核心工具包括：

| 工具名 | 作用 |
| --- | --- |
| `query_energy_metrics` | 查询指定建筑、时间段、指标的原始时序数据 |
| `query_daily_energy_summary` | 查询 `daily_energy_summary` 物化视图，获取日级趋势汇总 |
| `compare_metric_across_buildings` | 对多栋楼在同一时段内做横向指标对比 |
| `list_available_buildings` | 列出当前数据库中的合法楼宇及其设备 |
| `get_device_live_status` | 查询设备最新快照，支撑状态查看与异常追踪 |
| `calculate_system_cop` | 计算系统 COP 代理值，并与 GB 参考基准对比 |
| `detect_energy_anomalies` | 基于规则与阈值做异常识别与根因诊断 |
| `get_building_rated_values` | 读取额定值/期望值并与实际值并排对比 |
| `building_kpi_forecast_6h_12h` | 预测未来 6/12 小时关键 KPI 风险 |
| `generate_report` | 生成统计报表和下载入口 |


这意味着自然语言查询并不是“模型直接编答案”，而是“模型理解问题 -> 调用真实工具 -> 基于真实返回结果组织回答”。对赛题来说，这种方式更容易解释准确性来源，也更符合“基于 MCP 协议开发数据接入与查询接口”的要求。

#### 1.4.3 图表与报表设计
系统不仅返回文本结果，还会通过 artifact 机制返回 `LineChart`、`BarChart`、`Gauge`、`WorkOrderCard`、`ReportDownload` 等可直接渲染的结构化组件。也就是说，AI 输出并不是只有一段话，而是可以连同图表、指标卡和下载按钮一起返回。这部分正好对齐了赛题提出的“可视化图表展示”和“统计报表导出”要求。

### 1.5 LangGraph + MCP + RAG 的智能分析设计
系统的智能分析链路采用“LangGraph 编排 + MCP 工具调用 + RAG 知识增强”的组合方式，而不是让一个大模型单独承担全部理解、查询和决策任务。

#### 1.5.1 智能体分工
当前智能链路主要由三类职责构成：

+ `Router Agent`：判断问题属于查询、对比、预测、诊断还是知识检索。
+ `Data Agent`：基于 MCP 工具拿数、生成图表 artifact、整理结构化事实。
+ `Diagnose Agent`：结合异常事件、上下文事件、知识库和工单上下文进行原因解释和处置建议推理。

这种拆分的意义在于：

1. 把“理解问题”和“执行数据查询”分开，降低幻觉风险。
2. 把“事实生成”和“诊断建议”分开，避免所有逻辑压在一次输出上。
3. 便于后续单独升级某一层能力，例如新增新工具、替换知识检索策略、增强诊断规则。

#### 1.5.2 SSE 流式交互设计
Web 管理端和 AI 控制台采用统一的 SSE 对话接口。服务端会按 `thinking`、`text`、`artifact`、`done` 等事件持续返回中间结果。这样做的好处有三点：

+ 用户可以看到系统正在做什么，降低等待不确定性。
+ 图表和工单卡片可以先于最终总结返回，增强交互性。
+ 前端可以在同一轮对话中承接分析、展示和下一步操作，不必反复跳页面。

因此，这套交互不是单纯“把 REST 改成 SSE”，而是让智能分析、图表渲染和业务动作提示进入同一条用户体验链路。

#### 1.5.3 RAGFlow 与知识增强设计
赛题要求系统能够构建知识库并支撑运维问答。当前项目中，文档知识主要通过数据中心上传 PDF、DOCX、TXT、Markdown 等文档后接入 RAGFlow；现场经验则通过工单反馈与维修经验表持续沉淀。系统最终形成“文档知识 + 经验知识”两类知识源：

+ 文档知识：偏规范、手册、标准和设备说明书。
+ 经验知识：偏现场维修结论、常见故障处理路径和实践反馈。

当主知识库召回不足时，系统还保留了两层兜底：

1. 本地知识片段兜底，保证核心问答不会因外部服务异常而完全失效。
2. 在显式开启 `enable_web_search` 时，通过 `web_search` 获取外部公开资料做补充检索。

因此，知识增强链路不是单点依赖，而是“RAGFlow 优先、本地兜底、联网补充可选”的稳健结构。

### 1.6 AI 运维、工单审批与智能派单设计
智慧运维模块并不是单一问答模块，而是把异常、预测、审批、派工、执行和经验沉淀放在一条连续业务链里。

#### 1.6.1 异常与预警前移
系统同时提供两种风险入口：

+ 实时异常检测：基于 `energy_data` 与 `kpi_expected_hourly` 的偏差检测结果写入 `anomaly_events`。
+ 预测预警：基于未来 6/12 小时 KPI 预测结果写入 `predicted_anomaly_events`。

前者回答“已经出问题了没有”，后者回答“接下来会不会出问题”。两条链路最终都可以进入工单体系，因此调度端不需要维护两套完全不同的处理方式。

其中，“实时异常检测”在系统设计里不是只表示“最后有一张异常事件表”，而是有明确的链路支撑：

1. 数据进入检测链路：楼宇时序数据可以通过数据中心的流式导入接口或 `energy_data` 行级写入接口进入库内；一旦新数据入库，就可以复用同一套期望值计算服务生成对应时段的 `kpi_expected_hourly` 基线。
2. 检测触发机制：当前演示环境默认未开启常驻实时任务，主要通过管理员手动触发 `/api/admin/detect-anomalies` 或 `/api/admin/rebuild-all` 完成重建；但后端已预留后台周期任务开关，部署时可通过 `ENABLE_STARTUP_JOBS`、`ENABLE_ANOMALY_JOB` 启动整点自动检测，也可以在新数据写入后按楼宇、按时间戳调用增量刷新服务，形成准实时检测链路。
3. 检测结果落库方式：检测服务会先生成小时级 `kpi_anomaly_flags`，再汇总形成 `anomaly_events`，同时派生设备状态与异常归因信息，保证后续页面展示、诊断解释和设备追踪都基于同一份异常事实。
4. 检测后的业务闭环：`anomaly_events` 不会停留在“告警结果”层，而是继续合并为 `incident`，并生成或复用 `work_order`；如果开启自动流程，还会继续进入 AI 审批、待派工、智能派单/共享工单大厅以及通知推送链路。

因此，本文所说的“实时异常检测”，更准确地说是“系统结构具备把新到数据快速转为异常事件并推进处置流程的能力”。答辩时也可以明确说明：当前项目默认没有在演示环境中持续开启该任务，但架构和服务拆分已经为实时化部署预留好了接口与调度能力。

#### 1.6.2 AI 审批设计
工单审批不是单纯看异常值大小，而是结合 `context_events` 中的装修、加班、维护窗口、极端天气等背景事件判断异常是否合理。当前审批思路是：

1. 先查异常发生时间附近是否存在生效上下文事件。
2. 如果没有相关事件，默认更偏向继续处置。
3. 如果有相关事件，再交由模型判断这些背景是否足以解释当前异常。
4. 无论结果如何，都记录到 `work_order_audit_log` 中，形成可追溯审计链。

这样做的好处是，AI 审批被限制在“解释异常是否合理”这一窄问题上，而不是让模型直接自由决定整个工单命运，可靠性更高。

#### 1.6.3 智能派单与共享工单大厅
当工单进入待派工阶段后，系统会基于人员技能、班组、楼宇覆盖、值班状态、当前负载等因素对候选人做规则评分，选择推荐维修人员。  
如果出现无人接单、超时待接管或复杂协同场景，系统会把事项放入共享工单大厅，由 `dispatch_hall_entries` 和 `dispatch_hall_applications` 承接跨人员、跨班组的二次协同处理。

这一设计对应的不是单一“派给某人”动作，而是完整的调度能力：

+ 推荐派单
+ 自动重派评估
+ 超时接管
+ 共享大厅协同
+ 通知触发与关闭

因此，工单链路不是单线流转，而是可在异常复杂度提升时自然切换到协同模式。

### 1.7 多端协同设计
当前系统按角色和工作场景拆分为三类入口：

| 端 | 核心用户 | 主要职责 |
| --- | --- | --- |
| Web 管理端 | `admin`、`manager` | 首页总览、查询统计、数据中心、AI 审批、派工与运营分析 |
| 移动运维端 | `admin`、`manager` | 只读分析、异常跟踪、派工状态查看、运营洞察 |
| 移动维修端 | `ops` | 接单、到场、开始处理、协同、反馈、维小修指导 |


三类入口共用同一业务底座，但职责边界清晰：

+ 管理端强调判断、审批与调度。
+ 维修端强调动作推进与现场反馈。
+ AI 助手提供分析和建议，但不绕过正式业务接口直接改状态。

这种设计避免了“维修人员接触过多后台配置”或“管理端承担现场执行动作”的角色错位问题。

### 1.8 可靠性、性能与扩展性设计
为了满足赛题提出的响应速度和稳定性要求，系统在工程实现上做了以下设计：

+ 使用 `daily_energy_summary` 物化视图承接高频日级聚合查询。
+ 使用 Redis cache-aside 模式缓存高频总览与列表数据。
+ Redis 不可用时自动退化到本地 TTL 缓存，避免系统整体不可用。
+ 通过异步任务和独立 Worker 承担预测、模型推理等相对重的计算任务。
+ 通过 `work_order_audit_log`、`dispatch_events` 等审计表保留关键状态变更轨迹。
+ 通过兼容性初始化逻辑在启动阶段补齐旧表结构和视图，降低环境差异风险。

从扩展性看，当前架构已经具备继续增加新楼宇、新设备类型、新工具、新知识源和新前端入口的基础，不会因为某一层变化而导致系统整体重构。
