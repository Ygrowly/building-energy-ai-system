# 楼宇能耗与异常检测系统 - 数据库详细设计文档
## 1. 架构与设计理念 (Architecture & Philosophy)
本系统采用**“物理实体（楼宇/设备） + 时序事实（能耗） + 业务闭环（告警）”**的四层架构设计，完全符合关系型数据库第三范式（3NF），并针对时序数据的海量读写场景进行了工程化优化。

### 核心设计原则：
1. **多租户与层级管控**：以 `buildings` 为顶层实体，向下辐射。预留扩展性，方便后续通过楼宇隔离不同租户的数据。
2. **生命周期强一致性 (Cascading)**：通过 `ON DELETE CASCADE` 外键约束，实现“删楼宇即删设备、删能耗、删告警”的自动化垃圾数据回收。
3. **单一事实来源 (SSOT)**：摒弃了在异常表中冗余存储“建筑类型”等极易变更的静态属性，强制通过 `JOIN` 关联查询，确保数据不冲突。
4. **幂等性与高并发**：异常表引入 `UUID` 主键和复合唯一约束（时间+建筑+规则），保证在高并发扫描下，同一异常不会被重复写入。

## 2. 实体关系图 (ER 模型)
```latex
[ buildings ] (楼宇/站点) 
   │
   ├── (1:N) ──> [ devices ] (计量设备/传感器)
   │
   ├── (1:N) ──> [ energy_data ] (时序能耗事实表)
   │
   └── (1:N) ──> [ anomaly_events ] (异常事件业务表)
```

_(注：_`energy_data`_ 和 _`anomaly_events`_ 为了极致的查询性能，直接外键关联至 _`buildings`_，从而避免了每次查询都需要经过 _`devices`_ 表的深度 Join 开销，这是典型的时序架构优化。)_

## 3. 数据库表结构与 DDL 语句 (PostgreSQL)
请在您的数据库中按顺序执行以下完整 SQL 脚本：

### 3.1 楼宇表 (buildings)
**职责**：存储楼宇静态元数据，作为权限和报表的最小物理分组单位。

```sql
CREATE TABLE IF NOT EXISTS buildings (
    building_id         TEXT PRIMARY KEY,
    primary_space_usage TEXT,               -- 建筑用途 (例: Education, Office)
    sqm                 REAL,               -- 建筑面积 (平方米)
    timezone            TEXT DEFAULT 'UTC'  -- 时区 (用于当地时间按天/月聚合)
);

-- 索引：加速按建筑类型的分类统计
CREATE INDEX idx_buildings_usage ON buildings(primary_space_usage);
```

### 3.2 设备表 (devices)
**职责**：记录设备的静态信息及设备类型映射。

```sql
CREATE TABLE IF NOT EXISTS devices (
    device_id    TEXT PRIMARY KEY,
    building_id  TEXT NOT NULL REFERENCES buildings(building_id) ON DELETE CASCADE,
    device_type  TEXT NOT NULL              -- 设备类型 (例: ElectricityMeter, HVAC)
);

-- 索引：加速查找某栋楼下的所有设备
CREATE INDEX idx_devices_building ON devices(building_id);
```

### 3.3 能耗时序宽表 (energy_data)
**职责**：存储设备周期性上报的度量值，是整个系统写入最密集的“事实表”。

```sql
CREATE TABLE IF NOT EXISTS energy_data (
    "timestamp"          TIMESTAMPTZ NOT NULL,
    building_id         TEXT NOT NULL REFERENCES buildings(building_id) ON DELETE CASCADE,
    
    -- 资源能耗指标
    electricity_kwh     REAL,
    water_m3            REAL,
    hotwater_kwh        REAL,
    chilledwater_kwh    REAL,
    
    -- HVAC与环境系统指标
    sim_supply_temp_c   REAL,
    sim_return_temp_c   REAL,
    air_temp_c          REAL,
    dew_temp_c          REAL,
    humidity_rh_pct     REAL,
    
    -- 原始数据自带的状态标识
    anomaly_status      TEXT                -- 'normal' 或 'anomaly'
);

-- 复合索引：完美覆盖 "查询某栋楼某段时间的能耗" (Dashboard核心查询)
CREATE INDEX idx_energy_building_ts ON energy_data(building_id, "timestamp" DESC);

-- 单列索引：用于全局时间范围跨楼宇分析
CREATE INDEX idx_energy_ts ON energy_data("timestamp");

-- 单列索引：用于快速过滤整体异常比例
CREATE INDEX idx_energy_status ON energy_data(anomaly_status);
```

### 3.4 异常事件表 (anomaly_events)
**职责**：记录算法或规则引擎检测到的异常，包含状态跟踪，支持运维闭环。

```sql
CREATE TABLE IF NOT EXISTS anomaly_events (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    detected_at      TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP, -- 系统发现时间
    data_timestamp   TIMESTAMPTZ NOT NULL,                           -- 数据本身的原始时间
    building_id      TEXT NOT NULL REFERENCES buildings(building_id) ON DELETE CASCADE,
    meter_device_id  TEXT NOT NULL,
    rule_triggered   TEXT NOT NULL,                                  -- 触发的规则名
    actual_value     REAL,                                           -- 实际测得值
    threshold_value  REAL,                                           -- 报警阈值
    message          TEXT,                                           -- 详细描述
    is_resolved      BOOLEAN NOT NULL DEFAULT FALSE                  -- 运维处理状态
);

-- 幂等性约束：保证 [同一时间 + 同一建筑 + 同一规则] 绝不会产生重复告警
ALTER TABLE anomaly_events
    ADD CONSTRAINT uq_anomaly_event UNIQUE (data_timestamp, building_id, rule_triggered);

-- 索引：按发生时间倒序查询
CREATE INDEX idx_anomaly_events_data_timestamp ON anomaly_events (data_timestamp DESC);

-- 复合索引：查看特定楼宇的历史异常记录
CREATE INDEX idx_anomaly_events_building_ts ON anomaly_events (building_id, data_timestamp DESC);

-- 局部索引 (Partial Index) 超级优化：只为未解决的告警建索引，极速刷新监控大屏
CREATE INDEX idx_anomaly_events_unresolved ON anomaly_events (data_timestamp DESC) 
    WHERE is_resolved = FALSE;
```

## 4. 经典业务场景与查询示例 (SQL 实战)
此结构设计旨在让复杂业务查询变得极为高效，以下是三个核心场景的查询 SQL：

### 场景 1：能耗监控大屏（按日统计特定建筑的冷热空调总能耗）
```sql
SELECT 
    date_trunc('day', "timestamp") AS report_day,
    SUM(hotwater_kwh + chilledwater_kwh) AS total_hvac_energy
FROM energy_data
WHERE building_id = 'Fox_public_Henr'
  AND "timestamp" >= '2016-01-01' AND "timestamp" < '2016-02-01'
GROUP BY report_day
ORDER BY report_day DESC;
```

### 场景 2：运维告警工作台（查询所有未解决的告警及建筑属性）
利用单一事实来源设计，动态拉取 `primary_space_usage`：

```sql
SELECT 
    ae.data_timestamp,
    ae.building_id,
    b.primary_space_usage AS building_type,
    ae.rule_triggered,
    ae.actual_value,
    ae.message
FROM anomaly_events ae
JOIN buildings b ON ae.building_id = b.building_id
WHERE ae.is_resolved = FALSE
ORDER BY ae.data_timestamp DESC;
```

### 场景 3：能效基准分析（对比不同类型建筑的单位面积平均电耗）
```sql
SELECT 
    b.primary_space_usage,
    SUM(e.electricity_kwh) / SUM(DISTINCT b.sqm) AS kwh_per_sqm
FROM buildings b
JOIN energy_data e ON b.building_id = e.building_id
WHERE e.anomaly_status = 'normal' -- 仅计算正常运行时期的数据
GROUP BY b.primary_space_usage;
```

## 5. 后续架构演进建议 (Scalability)
随着系统运行，`energy_data` 表的数据量将快速膨胀，建议采取以下演进路线：

1. **超大规模支持**：当行数突破千万级，强烈建议引入 **TimescaleDB** 插件，将 `energy_data` 转化为超表（Hypertable），获得高达 10 倍以上的时序读写性能提升。
2. **灵活扩展**：若未来需要接入不支持的设备属性（如设备的 MAC 地址、固件版本），可在 `devices` 表中新增一列 `metadata JSONB`，无需频繁修改表结构即可实现高扩展。
3. **数据质量标识**：若未来传感器存在断线补录情况，可在 `energy_data` 中增加 `quality_flag TEXT` 字段，区分数据是“真实测量”还是“插值估算”。
