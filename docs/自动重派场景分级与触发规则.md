# 自动重派场景分级与触发规则

## 1. 目的

本文用于回答两个问题：

1. 在当前派单系统里，什么情况应被认定为“需要换责任人”。
2. 这些情况里，哪些适合进入自动重派，哪些仍应由管理员最终处理。

本文刻意区分以下几类动作，避免把不同语义混在一起：

- `正式重派`：当前 `dispatch_task` 还在执行，把旧任务转为 `transferred`，再创建新的正式派工。
- `重新派工`：当前 `dispatch_task` 已经结束，例如 `rejected / cancelled`，工单仍需继续处理，再重新派给别人。
- `协同支援`：当前主责任人继续持有工单，但需要别人协同，不属于换主责任人。
- `大厅接管`：当前主责任人暂未移除，先开放 `takeover_candidate`，等待管理员确认是否正式接管。

---

## 2. 当前系统边界

### 2.1 当前已落地的相关状态

- 活跃派工状态：`assigned / accepted / arrived / processing / waiting_support`
- 结束态：`completed / cancelled / transferred / rejected / escalated`
- 大厅类型：
  - `support_request`
  - `takeover_candidate`
- 自动派工复核状态：
  - `pending`
  - `reviewed`
  - `needs_reassign`

### 2.2 当前自动重派执行器的保守边界

当前 `POST /api/work-orders/{ticket_id}/auto-reassign` 是一个受 feature flag 控制的执行器。  
它当前默认只适用于：

- 工单仍为 `dispatched`
- 存在 `current_dispatch`
- 当前派工状态属于 `assigned / accepted / arrived / processing`
- 默认要求当前派工已 `overdue`
- 未达到最大改派尝试次数
- 存在明显更优的新候选人

这意味着：

- 它不是“所有需要换责任人情况”的总代表。
- 它只是“目前适合保守自动评估并可能自动执行”的一部分。

### 2.3 当前已落地的一期触发器

当前代码已把一期自动重派触发器接到 `scan_dispatch_sla_states`：

- `assigned -> overdue` 可触发自动重派评估
- `accepted -> overdue` 可触发自动重派评估
- 当前责任人客观不可用时，也可触发自动重派评估

但默认仍保持关闭，需同时显式开启：

- `ENABLE_AUTO_REASSIGN_EXECUTION=true`
- `ENABLE_AUTO_REASSIGN_PHASE1_TRIGGER=true`

并可用以下参数收紧触发范围：

- `AUTO_REASSIGN_TRIGGER_ASSIGNED_OVERDUE`
- `AUTO_REASSIGN_TRIGGER_ACCEPTED_OVERDUE`
- `AUTO_REASSIGN_ACCEPTED_MIN_PREVIOUS_REMINDERS`
- `AUTO_REASSIGN_TRIGGER_ASSIGNEE_UNAVAILABLE`

同时也已补上“真执行灰度闸门”，仅作用于自动触发的自动重派执行，不影响管理员手动调用执行器：

- `AUTO_REASSIGN_ALLOWED_BUILDINGS`
- `AUTO_REASSIGN_ALLOWED_PRIORITIES`
- `AUTO_REASSIGN_ALLOWED_REQUIRED_SKILLS`

未命中安全改派条件时：

- 超时场景继续走 `takeover_candidate`
- 当前责任人客观不可用但无法安全改派时，也会开放大厅待接管

### 2.4 当前已落地的影子观察模式

当前代码已补上自动重派一期的影子观察模式，用于解决“不开真执行就无法观测触发质量”的问题。

需显式开启：

- `ENABLE_AUTO_REASSIGN_PHASE1_TRIGGER=true`
- `ENABLE_AUTO_REASSIGN_SHADOW_MODE=true`

影子模式下：

- 仍按一期三类触发器命中：
  - `assigned -> overdue`
  - `accepted -> overdue`
  - 当前责任人客观不可用
- 会执行只读 `auto-reassign evaluation`
- 会写入审计日志 `auto_reassign_shadow_evaluated`
- 不会直接正式改派

影子模式记录的核心事实包括：

- 触发原因
- 当前派工阶段
- 当前责任人
- 是否落在当前真执行灰度内
- 候选人、分差、规则阈值
- 阻断原因
- `would_execute`
- `would_execute_in_rollout`
- `would_hall_fallback`

说明：

- 影子模式只禁止“自动重派执行”本身，不会改变原有的超时事件写入。
- 对于 `assigned / accepted -> overdue` 这类本来就应开放大厅的场景，现有 SLA 扫描的大厦待接管逻辑仍保持原样。
- `当前责任人客观不可用` 这类非超时触发，在影子模式下只记录“理论上是否会开大厅”，不会额外真实创建大厅条目。

## 3. 分级原则

本文把“需要换责任人”的场景分为 3 档运营等级，并额外列出一档“非重派路径”。

### A 档：必须换责任人

含义：

- 当前责任人已经不适合继续持有工单。
- 运营语义上应尽快完成换人。
- 其中有些走 `正式重派`，有些走 `重新派工`，取决于当前派工是否仍活跃。

### B 档：默认进入重派评估

含义：

- 当前责任人未必已经失效，但继续持有风险明显升高。
- 系统应主动进入评估，优先给出候选人、分差、风险和推荐动作。
- 其中部分场景可在规则稳定后纳入自动重派。

### C 档：仅人工复核后重派

含义：

- 业务上可能需要换人，但交接成本高、现场连续性强或语义容易和协同混淆。
- 系统可以提示、排序、推荐，但不应默认自动执行。

### X 档：非重派路径

含义：

- 这些场景虽然也会“卡住”，但不应归入换主责任人。
- 应分别走协同、大厅、首次派工或数据修复路径。

---

## 4. 需要换责任人的情况全集

| 编号 | 场景 | 当前系统信号 | 应走路径 | 等级 | 是否建议纳入自动重派 |
|------|------|-------------|---------|------|----------------------|
| A1 | 维修员明确拒单 | `dispatch_status = rejected`，有 `reject_reason` | 重新派工 | A | 否。应走“自动重新派工”而不是 `auto-reassign` |
| A2 | 管理员主动取消当前派工且工单仍需继续处理 | `dispatch_status = cancelled`，工单未关闭 | 重新派工 | A | 否。属于取消后重新派工 |
| A3 | 当前责任人已不可用 | `user.is_active = false`、`dispatch_enabled = false`、班次已不满足派工要求 | 正式重派 | A | 是，适合纳入自动重派一期 |
| A4 | 当前主责任人专业明显不匹配 | 现场反馈主技能方向错误，当前人不应再做主责任人 | 正式重派 | A | 部分适合，需先把“误派”证据结构化 |
| A5 | 管理员明确认定派错人 | 管理员人工判断、现场变化、调度纠偏 | 正式重派 | A | 否，保留人工最终确认 |
| A6 | 自动派工复核被标记 `needs_reassign` | `admin_action = auto_dispatch_needs_reassign` 或复核状态为 `needs_reassign` | 正式重派 | A | 部分适合，建议先保留人工确认 |
| B1 | 未接单超时 | `dispatch_status = assigned` 且 `timeout_level = overdue` | 正式重派 / 大厅待接管 | B | 是，最适合自动重派一期 |
| B2 | 已接单但未到场超时 | `dispatch_status = accepted` 且 `timeout_level = overdue` | 正式重派 / 大厅待接管 | B | 是，但建议比 B1 更保守 |
| B3 | 已到场或处理中长期超时且无有效推进 | `arrived / processing` 且 `timeout_level = overdue`，进度长期无变化 | 正式重派 / 大厅待接管 | B | 暂不建议一期自动执行，先以评估和大厅兜底为主 |
| B4 | 多次催办仍无动作 | `reminder_count` 持续增加且状态未推进 | 正式重派评估 | B | 可作为附加触发信号，不建议单独自动执行 |
| B5 | 已进入 `takeover_candidate` 待接管 | 已创建或重开接管大厅条目 | 大厅接管 -> 正式重派 | B | 否。先开放大厅，再由管理员确认接管 |
| C1 | 高优先级现场已形成连续作业，不宜贸然换人 | 已到场、已开始处理、现场切换成本高 | 人工复核后决定是否重派 | C | 否 |
| C2 | 当前人能做，但出现明显更优候选人 | 候选人分数更高、负载更低、距离更近 | 人工复核后决定是否重派 | C | 否，不能只靠推荐分自动换人 |
| C3 | 班组、区域、班次责任发生变化 | 夜班切换、楼宇责任切换、调度边界调整 | 人工复核后决定是否重派 | C | 否 |
| C4 | 当前任务卡在复杂现场问题，是否换人依赖业务判断 | 现场信息不完整、交接成本高、可能需要升级或协同 | 人工复核后决定是否重派 | C | 否 |

## 5. 不应归入重派的情况

这些情况会卡住执行，但默认不应归为“换主责任人”。

| 编号 | 场景 | 当前系统信号 | 正确路径 | 原因 |
|------|------|-------------|---------|------|
| X1 | 待协同 | `dispatch_status = waiting_support` | 协同支援 / `support_request` | 主责任人仍成立，只是需要帮助 |
| X2 | 等待配件 | `worker_result = needs_parts` 或进入 `waiting_support` | 协同支援 / 支持链路 | 这是资源阻塞，不是天然要换责任人 |
| X3 | 普通 `pending_dispatch` | 尚无当前责任人 | 首次派工 | 还没派出去，谈不上重派 |
| X4 | 工单已结束 | `completed / false_alarm / closed` | 无需重派 | 责任链已结束 |
| X5 | 当前派工已 `transferred` | 已发生正式改派 | 查看历史，不重复触发 | 这是已完成的重派结果 |
| X6 | 数据脏状态 | 工单在执行中但缺少 `current_dispatch` | 数据修复 | 先修状态，再决定是否派人 |
| X7 | 单纯分数更高但当前执行正常 | 当前人未超时、未阻塞、现场推进正常 | 保持现状 | 不能把推荐器变成频繁换人的放大器 |

## 6. 自动重派触发规则

## 6.1 总原则

自动重派必须同时满足四个条件：

1. 工单仍需继续处理。
2. 当前责任人继续持有工单已经不合理。
3. 新候选人明显更适合接手。
4. 换人带来的收益大于交接成本。

这四个条件缺一不可。

## 6.2 一期建议允许自动执行的触发器

一期建议只开放“换人收益高、交接成本低”的场景：

### T1. 未接单超时

- 条件：
  - `work_order.status = dispatched`
  - `current_dispatch.dispatch_status = assigned`
  - `timeout_level = overdue`
  - 存在符合阈值的新候选人
- 动作优先级：
  1. 自动重派
  2. 若无安全候选人，则保留或创建 `takeover_candidate`

### T2. 已接单但未到场超时

- 条件：
  - `current_dispatch.dispatch_status = accepted`
  - `timeout_level = overdue`
  - 当前责任人未到场
  - 存在符合阈值的新候选人
- 建议：
  - 可以纳入自动重派，但阈值应比 T1 更保守
  - 最好叠加“至少已催办一次仍无动作”

### T3. 当前责任人客观不可用

- 条件：
  - 当前责任人停用、离岗、班次不满足或被禁派
  - 当前任务尚未进入高交接成本阶段
  - 存在符合阈值的新候选人
- 建议：
  - 这是自动重派一期最有业务合理性的触发器之一

## 6.3 二期再考虑自动执行的触发器

这些场景建议先做“自动评估 + 推荐 + 大厅兜底”，后续再视稳定性决定是否真正自动执行：

- `arrived / processing` 超时但无有效推进
- 自动派工复核被标记 `needs_reassign`
- 多次催办无动作
- 大厅已有接管意愿且当前责任人仍无恢复迹象

## 6.4 默认阻断条件

只要命中以下任一条件，就不应自动执行：

- 工单不是 `dispatched`
- 不存在 `current_dispatch`
- 当前派工状态不在允许范围内
- 已达到最大改派尝试次数
- 没有明显更优的新候选人
- 第一候选人未值班、未启用或已不可派
- 第一候选人与第二候选人分差不够
- 当前任务处于高交接成本阶段且没有人工确认
- 当前更像协同问题，而不是换主责任人问题

## 7. 推荐的自动重派分阶段上线口径

## 7.1 阶段一：严格保守

只自动处理：

- B1 未接单超时
- B2 已接单未到场超时
- A3 当前责任人客观不可用

但第一批真实放量建议进一步收紧为：

- 先只打开 `B1 未接单超时`
- `B2 / A3` 继续保留影子观察
- 真执行必须叠加楼宇、优先级、技能灰度闸门

建议第一批口径：

- `ENABLE_AUTO_REASSIGN_PHASE1_TRIGGER=true`
- `ENABLE_AUTO_REASSIGN_EXECUTION=true`
- `AUTO_REASSIGN_TRIGGER_ASSIGNED_OVERDUE=true`
- `AUTO_REASSIGN_TRIGGER_ACCEPTED_OVERDUE=false`
- `AUTO_REASSIGN_TRIGGER_ASSIGNEE_UNAVAILABLE=false`
- `AUTO_REASSIGN_ALLOWED_BUILDINGS=<首批楼宇>`
- `AUTO_REASSIGN_ALLOWED_PRIORITIES=<首批优先级>`
- `AUTO_REASSIGN_ALLOWED_REQUIRED_SKILLS=<首批技能>`

不自动处理：

- `arrived / processing / waiting_support`
- 自动派工复核 `needs_reassign`
- 大厅接管申请

## 7.2 阶段二：加入更多评估型场景

在阶段一稳定后，再考虑放开：

- B3 已到场或处理中长期超时
- B4 多次催办无动作
- A6 自动派工复核 `needs_reassign`

但仍建议保留：

- 大厅待接管
- 人工最终确认或回滚能力

## 7.3 阶段三：形成完整闭环

最终闭环应是：

1. SLA 或状态变化触发重派评估
2. 命中自动条件则自动执行正式重派
3. 不命中则进入大厅待接管或保留人工处理
4. 全链路记录审计日志、触发原因、原责任人、新责任人、候选人分数和回滚依据

---

## 8. 当前建议的运营口径

如果只用一句话描述当前最稳妥的策略，建议定成：

> 只在“未接单超时、已接单未到场超时、当前责任人客观不可用”三类低交接成本场景开放真正自动重派；拒单/取消走重新派工，协同和配件走支持链路，处理中长时间卡住的工单保留人工复核与大厅接管。

---

## 9. 待运营确认的参数

后续真正开启 `ENABLE_AUTO_REASSIGN_EXECUTION` 前，至少要确认以下三项：

1. `accepted -> overdue` 需要先催办几次才允许自动重派。
2. `arrived / processing` 是否允许任何形式的自动重派，还是永远只做建议和大厅兜底。
3. 自动派工复核 `needs_reassign` 是否应直接进入自动重派，还是继续保持“管理员最终确认”。
