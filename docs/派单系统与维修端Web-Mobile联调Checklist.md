# 派单系统与维修端 Web / Mobile 联调 Checklist

## 1. 文档目的

本文档用于沉淀派单系统在 **Web 管理端 + Mobile 管理端 + Mobile 维修端 + 后端 + 真实数据库** 上线前的人工联调检查项。

它不是替代自动化测试，而是用于回答下面这些问题：

- 这套真实派工工作台在多端是否真的能跑通
- 同一条派工链路在 Web、Mobile、后端时间线、数据库投影上是否一致
- 批量派工、失败重试、人工复核、改派、协同、关闭等关键动作是否都能闭环
- 发版前到底应该人工核对哪些点，避免“接口通了但业务没真正通”

---

## 2. 适用范围

本清单适用于当前已经落地的能力：

- `pending_dispatch -> dispatched -> completed -> closed` 主链路
- 候选人推荐、手动派工、批量派工
- 接单、到场、开始处理、申请协同、恢复处理、完成处理
- 催办、联系责任人、改派、取消派工
- Web / Mobile 的时间线、消息中心、当前责任人展示
- `dispatch_tasks / dispatch_events / current_dispatch` 一致性核验

---

## 3. 使用方式

建议每次上线前至少执行一次完整联调，或者在以下场景执行：

- 后端改了派工、执行、SLA、通知逻辑
- Web 工单页、Mobile 管理端、Mobile 维修端有状态展示改动
- 数据库执行了 `017 / 018 / 019` 相关迁移
- 真实库做过修复、回填、批量派工试运行

建议执行顺序：

1. 先跑“环境与账号准备”
2. 再跑“单张派工主链路”
3. 再跑“批量派工与失败闭环”
4. 再跑“维修执行与调度动作”
5. 最后跑“巡检脚本与上线结论”

## 4. 环境准备

### 4.1 服务状态

- [ ] `backend` 已启动，API 可访问 `http://localhost:8000`
- [ ] `frontend` 已启动，可访问 Web 管理端
- [ ] `mobile` 已启动 `H5`，可访问移动端
- [ ] 前后端使用的是同一套后端环境与同一套数据库

### 4.2 建议账号

若当前环境沿用初始化脚本，可优先使用：

- 管理员 / 调度员：`test1 / test1234`
- 维修员：`ops_hvac_01 / test1234`
- 维修员：`ops_electrical_01 / test1234`
- 维修员：`ops_plumbing_01 / test1234`
- 维修员：`ops_controls_01 / test1234`
- 维修员：`ops_general_02 / test1234`

若当前环境不是这套账号，请替换成等价的真实账号，但必须满足：

- 至少 1 个 `manager/admin`
- 至少 2 个 `ops`
- `ops` 账号拥有 `worker_profiles`

### 4.3 数据前提

联调前建议数据库至少具备以下样本：

- [ ] 至少 `1` 张 `pending_dispatch` 工单
- [ ] 至少 `1` 张 `dispatched + pending_accept` 工单
- [ ] 至少 `1` 张 `dispatched + waiting_support` 工单
- [ ] 至少 `1` 张 `completed` 待关闭工单

如果样本不足，可用当前工作台手动制造，或者使用已有试运行数据。

## 5. 通过 / 阻塞标准

### 5.1 阻塞上线

出现以下任一情况，应视为阻塞上线：

- [ ] Web 派工成功，但 Mobile 维修端看不到工单
- [ ] Mobile 维修端动作成功，但 Web 时间线或状态没有更新
- [ ] 当前责任人、当前派工批次、时间线三者明显不一致
- [ ] 非责任维修员仍可推进别人的派工任务
- [ ] 批量派工后失败项无法继续处理
- [ ] 巡检脚本发现 `current_dispatch` 悬挂、冲突或投影不一致

### 5.2 非阻塞但需记录

- [ ] 文案不一致
- [ ] 时间显示格式不一致
- [ ] 消息顺序略有偏差，但状态正确
- [ ] 非关键页面刷新不及时，但手动刷新后数据正确

## 6. 单张派工主链路

### 6.1 Web 管理端手动派工

- [ ] 管理员登录 Web 工单页
- [ ] 在“待派工”中选中一张 `pending_dispatch` 工单
- [ ] 打开候选人面板，确认能看到候选人、推荐分、班组、负载
- [ ] 选择第一候选人并提交派工

预期结果：

- [ ] 工单从 `pending_dispatch` 转为 `dispatched`
- [ ] 当前责任人、责任班组、派工批次显示正确
- [ ] 时间线新增“人工派工”
- [ ] Mobile 管理端可看到该工单进入执行中
- [ ] 对应维修员在 Mobile 维修端能看到该工单

### 6.2 Mobile 管理端手动派工

- [ ] 管理员登录 Mobile 管理端
- [ ] 在“待派工”中选择一张工单
- [ ] 打开派工面板并提交派工

预期结果：

- [ ] Web 工单页能同步看到责任人和执行状态
- [ ] Mobile 维修端出现该工单
- [ ] 工单时间线与 Web 一致

---

## 7. 批量派工与失败闭环

### 7.1 Mobile 管理端批量推荐

- [ ] 打开“待派工”页
- [ ] 打开“批量推荐”
- [ ] 调整“本批次张数 / 优先级 / 单人批次上限”
- [ ] 查看推荐名单、当前负载、未纳入原因、未纳入示例

预期结果：

- [ ] 推荐结果会随着参数变化重新刷新
- [ ] 当前负载和本批次分配可解释
- [ ] 未纳入工单有明确原因，不是无提示消失

### 7.2 Mobile 管理端一键派工

- [ ] 对推荐结果执行“一键派工”

预期结果：

- [ ] 成功工单进入 `dispatched`
- [ ] 推荐工单从待派工列表减少
- [ ] Web 工单页能看到这些工单已进入执行中

### 7.3 Mobile 管理端失败闭环

- [ ] 若本轮有失败项，结果区应展示失败原因
- [ ] 对可重试项点击“重试”
- [ ] 对需要人工复核的项点击“人工复核”

预期结果：

- [ ] 可重试项能够单张或批量重试
- [ ] 人工复核会直接打开该工单派工面板
- [ ] 失败项不会只剩一段 toast 或弹窗文本

### 7.4 Web 管理端批量派工

- [ ] 在 Web 工单页“待派工”打开“批量推荐”
- [ ] 查看推荐、负载、未纳入原因
- [ ] 执行一键派工
- [ ] 对失败项执行“重试”或“人工复核”

预期结果：

- [ ] Web 端与 Mobile 管理端行为一致
- [ ] 人工复核能打开单张派工面板
- [ ] 批量结果区会保留失败项，不会直接消失

---

## 8. 维修执行链路

建议至少选 `1~2` 张已派工单，分别在 Mobile 维修端验证。

### 8.1 接单 / 到场 / 开始处理

- [ ] 责任维修员登录 Mobile 维修端
- [ ] 打开自己的工单
- [ ] 依次执行“确认接单 -> 确认到场 -> 开始处理”

预期结果：

- [ ] 每个动作都成功
- [ ] Web 管理端执行状态同步变化
- [ ] 时间线依次新增“已接单 / 已到场 / 开始处理”

### 8.2 申请协同 / 恢复处理

- [ ] 在处理中工单上执行“申请协同”
- [ ] 管理端确认工单进入 `waiting_support`
- [ ] 再执行“恢复处理”

预期结果：

- [ ] 阻塞原因展示正确
- [ ] 管理端可看到待协同状态
- [ ] 恢复处理后状态回到 `processing`
- [ ] 时间线包含“申请协同 / 协同解决”

### 8.3 完成处理

- [ ] 在 Mobile 维修端提交处理结果

预期结果：

- [ ] 工单进入 `completed`
- [ ] Web / Mobile 管理端都能看到“待关闭”
- [ ] 时间线新增“处理完成”

---

## 9. 调度动作链路

### 9.1 催办

- [ ] 在 Web 管理端对 `pending_accept / waiting_support / overdue` 工单执行“催办”
- [ ] 在 Mobile 管理端消息中心对执行提醒执行“催办”

预期结果：

- [ ] 后端产生 `reminded` 事件
- [ ] 时间线可见“调度催办”
- [ ] `reminder_count / last_reminded_at` 更新

### 9.2 联系责任人

- [ ] 在 Mobile 管理端点击“联系”

预期结果：

- [ ] 能正确拿到责任人联系方式
- [ ] 号码缺失时有明确提示

### 9.3 改派

- [ ] 对执行中工单执行“改派”
- [ ] 选择另一位维修员并提交

预期结果：

- [ ] 新责任人立即生效
- [ ] 派工批次增加
- [ ] 时间线新增“调度改派”
- [ ] 维修端只允许新责任人继续推进

### 9.4 取消派工

- [ ] 对 `pending_accept` 或 `accepted` 工单执行“取消派工”

预期结果：

- [ ] 当前派工任务被取消
- [ ] 工单不再显示旧责任人
- [ ] 时间线新增“取消派工”

---

## 10. 关闭链路

- [ ] 管理员在 Web 或 Mobile 管理端对 `completed / false_alarm / escalated` 工单执行关闭

预期结果：

- [ ] 工单进入 `closed`
- [ ] 执行中列表移除
- [ ] 已关闭列表可见
- [ ] 时间线闭环完整

---

## 11. 消息中心与时间线

### 11.1 Web 端

- [ ] 个人消息中心能看到待派工、执行提醒、待关闭消息
- [ ] 执行提醒支持催办、改派建议

### 11.2 Mobile 管理端

- [ ] 消息中心能看到执行提醒
- [ ] 提醒支持催办、联系、改派建议

### 11.3 时间线一致性

- [ ] 同一张工单在 Web 与 Mobile 展示的核心事件顺序一致
- [ ] 至少核对：派工、接单、到场、开始处理、协同、恢复、完成、关闭

---

## 12. 权限与异常场景

### 12.1 权限

- [ ] 非管理员不能执行管理动作
- [ ] 非责任维修员不能推进别人的派工任务
- [ ] 未登录或 token 失效后会回登录页

### 12.2 异常场景

- [ ] 候选人为空时，派工面板给出明确提示
- [ ] 重复点击已失效动作时，前端有兜底提示，后端不会写脏数据
- [ ] 批量派工失败后，失败项能被继续处理
