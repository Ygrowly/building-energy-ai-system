# 自动重派第一批灰度验收清单

## 1. 目的

本文用于验收“自动重派第一批真执行灰度”是否按预期工作。

本轮验收目标不是验证所有自动重派场景，而是只验证当前正式口径：

- 只开放 `assigned -> overdue`
- 只开放灰度范围：`Fox_public_Henry + high + hvac`
- `accepted -> overdue` 暂不自动重派
- `assignee_unavailable` 暂不自动重派
- `shadow mode` 保持开启

---

## 2. 当前灰度配置

当前环境应满足以下配置：

```env
ENABLE_AUTO_REASSIGN_PHASE1_TRIGGER=true
ENABLE_AUTO_REASSIGN_EXECUTION=true
ENABLE_AUTO_REASSIGN_SHADOW_MODE=true

AUTO_REASSIGN_ALLOWED_BUILDINGS=Fox_public_Henry
AUTO_REASSIGN_ALLOWED_PRIORITIES=high
AUTO_REASSIGN_ALLOWED_REQUIRED_SKILLS=hvac

AUTO_REASSIGN_TRIGGER_ASSIGNED_OVERDUE=true
AUTO_REASSIGN_TRIGGER_ACCEPTED_OVERDUE=false
AUTO_REASSIGN_TRIGGER_ASSIGNEE_UNAVAILABLE=false

AUTO_REASSIGN_MIN_SCORE=115
AUTO_REASSIGN_MIN_GAP=10
AUTO_REASSIGN_REQUIRE_ON_DUTY=true
AUTO_REASSIGN_REQUIRE_OVERDUE=true
AUTO_REASSIGN_MAX_ATTEMPT_NO=3
```

---

## 3. 验收入口

### 3.1 页面入口

- Web 前端：`http://localhost:5174/`
- 工单页：`派工中心 -> 洞察`

### 3.2 后端入口

- 健康检查：`GET http://localhost:8000/health`
- 手工触发 SLA 扫描：

```powershell
Invoke-WebRequest -Method Post http://localhost:8000/api/admin/scan-dispatch-sla -UseBasicParsing | Select-Object -Expand Content
```

说明：

- 当前环境默认不依赖后台定时器做验收。
- 验收时统一使用“手工触发 SLA 扫描”，不要靠等待分钟任务。

---

## 4. 验收准备

建议一次准备 3 张工单，分别验证：

1. 灰度内正例
2. 灰度外反例
3. 未开放触发器反例

### 4.1 A 单：灰度内正例

要求：

- 楼宇：`Fox_public_Henry`
- 优先级：`high`
- 技能：`hvac`
- 工单状态：`dispatched`
- 当前派工状态：`assigned`
- 当前维修员尚未接单

预期用途：

- 验证灰度内 `assigned -> overdue` 会自动重派

### 4.2 B 单：灰度外反例

要求：

- 当前派工状态仍为 `assigned`
- 但至少有一维不在灰度内：
  - 楼宇不是 `Fox_public_Henry`
  - 或优先级不是 `high`
  - 或技能不是 `hvac`

预期用途：

- 验证灰度外不会误自动重派

### 4.3 C 单：未开放触发器反例

要求：

- 工单仍在灰度范围内
- 当前派工状态：`accepted`
- 尚未到场

预期用途：

- 验证 `accepted -> overdue` 当前不会自动重派

---

## 5. 验收步骤

## 5.1 通用预检查

对每张工单先做以下确认：

1. 在工单列表或详情中记下 `ticket_id`
2. 确认工单当前状态为 `dispatched`
3. 确认存在 `current_dispatch`
4. 记录当前责任人姓名
5. 记录当前派工状态：`assigned / accepted`

如需做只读预检查，可调用：

```text
GET /api/work-orders/{ticket_id}/auto-reassign-evaluation?require_overdue=false
```

建议重点看：

- `eligible`
- `decision`
- `top_candidate`
- `blockers`

说明：

- 这里只是预检查，不代表系统此刻一定会执行自动重派。
- 真执行还受“是否超时”和“是否在自动触发灰度内”控制。

---

## 5.2 A 单验收：灰度内 `assigned -> overdue`

### 步骤

1. 打开 A 单详情，确认：
   - 楼宇、优先级、技能均在灰度范围内
   - 当前派工状态是 `assigned`
2. 记录当前责任人 `旧责任人`
3. 让 A 单进入接单超时
4. 手工调用一次 SLA 扫描
5. 回到工单详情刷新页面
6. 查看当前责任人是否变化
7. 查看时间线和最近审计记录
8. 查看派工洞察中的“自动重派一期 / 影子观察”

### 通过标准

必须同时满足：

- 当前责任人已变更
- 旧派工已变为 `transferred`
- 新派工为 `is_current=true`
- 时间线中能看到：
  - `已超时`
  - `自动重派已执行`
- SLA 扫描返回里：
  - `auto_reassign_triggers >= 1`
  - `auto_reassign_executed >= 1`
  - `auto_reassign_shadow_evaluated >= 1`
- 洞察里：
  - “灰度内会自动改派”有命中

### 判失败的典型现象

- 已经超时，但责任人没变
- 没有 `自动重派已执行`
- 影子里显示“理论可执行”，但真执行没有发生，且无灰度阻断理由

---

## 5.3 B 单验收：灰度外 `assigned -> overdue`

### 步骤

1. 打开 B 单详情，确认它至少有一维不在灰度范围内
2. 记录当前责任人 `旧责任人`
3. 让 B 单进入接单超时
4. 手工调用一次 SLA 扫描
5. 回到工单详情刷新页面
6. 查看当前责任人、时间线和大厅状态
7. 再到“自动重派一期 / 影子观察”中筛这张单

### 通过标准

必须同时满足：

- 当前责任人不变
- 没有出现 `自动重派已执行`
- 审计/时间线中能看到：
  - `自动重派灰度跳过`
- 若该场景应继续开放大厅，则会进入 `takeover_candidate`
- 影子观察中这条样本应表现为：
  - `灰度外`
  - 有明确的灰度阻断原因

### 判失败的典型现象

- 灰度外工单被直接自动改派
- 没改派，但也没有灰度跳过记录
- 洞察里看不出它为什么没执行

---

## 5.4 C 单验收：`accepted -> overdue`

### 步骤

1. 打开 C 单详情，确认：
   - 它在灰度范围内
   - 当前派工状态是 `accepted`
2. 记录当前责任人
3. 让 C 单进入“已接单未到场超时”
4. 手工调用一次 SLA 扫描
5. 回到工单详情刷新页面
6. 查看当前责任人和时间线

### 通过标准

必须同时满足：

- 当前责任人不变
- 没有出现 `自动重派已执行`
- 这张单不会因为本轮配置被自动重派
- 它继续走当前已有的超时处置链路

### 判失败的典型现象

- `accepted -> overdue` 被直接自动改派
- 配置明明关闭，但系统仍把这类单当一期真执行场景

---

## 6. 洞察页核查

进入：

- `派工中心 -> 洞察`
- 查看“自动重派一期 / 影子观察”

重点核查以下 4 个区域：

1. `触发评估`
   - 是否有本轮样本进入影子观察

2. `灰度内会自动改派`
   - A 单应带来增长

3. `灰度阻断`
   - B 单应带来增长

4. `最近影子评估`
   - A 单应显示 `灰度内`
   - B 单应显示 `灰度外`
   - C 单不应表现为真执行命中

---

## 7. 推荐验收结论

本轮验收通过，至少要能得出以下 3 条明确结论：

1. 灰度内 `assigned -> overdue` 会自动重派
2. 灰度外 `assigned -> overdue` 不会误自动重派，只会灰度跳过
3. `accepted -> overdue` 在当前配置下不会自动重派

如果三条里有任何一条无法成立，本轮灰度不应继续扩大。

## 8. 可选 SQL 核查

## 8.1 查派工链

```sql
select
  wo.ticket_id,
  wo.status,
  wo.current_dispatch_id,
  dt.id,
  dt.attempt_no,
  dt.is_current,
  dt.dispatch_status,
  dt.assigned_to,
  dt.timeout_level
from work_orders wo
left join dispatch_tasks dt on dt.work_order_id = wo.id
where wo.ticket_id = '你的ticket_id'
order by dt.attempt_no;
```

用途：

- 确认旧派工是否变 `transferred`
- 确认新派工是否成为 `current_dispatch`

## 8.2 查工单审计

```sql
select action, detail_json, created_at
from work_order_audit_log
where work_order_id = (
  select id from work_orders where ticket_id = '你的ticket_id'
)
order by created_at desc
limit 20;
```

重点看：

- `auto_reassign_executed`
- `auto_reassign_shadow_evaluated`
- `auto_reassign_rollout_skipped`

## 8.3 查大厅接管

```sql
select entry_type, status, reason, source_dispatch_id, created_at
from dispatch_hall_entries
where work_order_id = (
  select id from work_orders where ticket_id = '你的ticket_id'
)
order by created_at desc;
```

用途：

- 确认灰度外或未成功改派的场景是否继续进入大厅待接管

---

## 9. 回滚口径

如果验收过程中发现异常，可立即回滚到“仅影子观察”：

```env
ENABLE_AUTO_REASSIGN_EXECUTION=false
ENABLE_AUTO_REASSIGN_SHADOW_MODE=true
```

如需彻底停掉一期触发器：

```env
ENABLE_AUTO_REASSIGN_PHASE1_TRIGGER=false
ENABLE_AUTO_REASSIGN_EXECUTION=false
ENABLE_AUTO_REASSIGN_SHADOW_MODE=false
```

---

## 10. 验收记录模板

建议每张工单记录以下字段：

- `ticket_id`
- 场景：A / B / C
- 楼宇
- 优先级
- 技能
- 原责任人
- 超时前派工状态
- SLA 扫描时间
- 是否自动重派成功
- 是否命中灰度跳过
- 是否进入大厅
- 备注

只要把 A/B/C 三条都记录清楚，这一轮灰度是否继续扩就有依据了。
