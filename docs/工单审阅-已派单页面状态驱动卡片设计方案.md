# 工单审阅 - 已派单页面状态驱动卡片设计方案

## 1. 文档目标

本文档用于定义手机端 `工单审阅 > 已派单` 页的卡片设计方案，目标不是单纯补字段，而是建立一套可落地的 `状态驱动展示模型`，让运维人员在最短时间内完成以下判断：

1. 当前异常是否仍在持续。
2. 工单是否有人接、处理到哪一步。
3. 是否存在超时风险，是否需要催办或升级。
4. 现场人员下一步应该先看什么。

本文档适用于：

- 产品经理梳理信息架构与字段优先级
- UI 设计师输出高保真页面
- 前端开发改造 `已派单` 卡片与列表页
- 后端与接口设计补齐状态衍生字段

---

## 2. 设计背景

### 2.1 当前页面的问题

结合现有页面与组件实现，`已派单` 卡片当前更像“异常事件卡片”，而不是“工单执行卡片”，存在以下问题：

1. `工单推进信息不足`
   当前页面能看到异常严重程度，但看不到 `派给谁`、`接单没有`、`是否到场`、`是否快超时`。

2. `信息重心偏向异常描述`
   峰值偏差、连续次数、AI 分析展示较多，但在 `已派单` 阶段，运维管理者更关心执行进度。

3. `对象定位不够细`
   当前卡片多数只到 `楼栋` 级别，缺少 `楼层 / 系统 / 设备`，无法支持快速派工与复核。

4. `缺少行动导向`
   现有 AI 分析更像解释文本，缺少 `下一步建议动作` 和 `联系/催办/趋势` 等高频操作入口。

5. `缺少状态细分`
   `已派单` 只是一层总状态，无法区分是 `待接单`、`处理中` 还是 `已超时`。

### 2.2 运维视角下的核心认知

对建筑能耗运维人员来说，卡片不是为了“展示异常”，而是为了“支持决策”。  
在 `已派单` 页面，最重要的问题不是“异常多严重”，而是：

1. 这张单有没有失控。
2. 责任有没有落实。
3. 这次异常现在值不值得继续盯。
4. 我是不是要马上介入。

因此，`已派单` 页面必须从“事件中心”切换到“状态中心”。

---

## 3. 设计原则

### 3.1 总原则：统一骨架 + 状态驱动

所有卡片采用统一的结构骨架，但中间的重点信息必须随着 `工单状态` 变化。

### 3.2 双主线模型

卡片始终由两条信息主线构成：

| 主线 | 作用 | 在已派单页中的权重 |
|------|------|------------------|
| 异常事件线 | 告诉用户异常发生在哪里、严重到什么程度、现在是否仍异常 | 40% |
| 工单执行线 | 告诉用户谁在处理、处理到哪一步、是否超时、是否需要催办 | 60% |

在 `已派单` 页，执行线优先级高于异常线。

### 3.3 设计原则清单

1. `先状态，后细节`
   用户第一眼必须看到当前执行状态和 SLA 风险。

2. `先决策，后解释`
   先告诉用户要不要催办、联系谁、异常是否恢复，再展示 AI 原因解释。

3. `对象必须能定位到处理单元`
   至少展示到 `楼栋 / 楼层 / 系统 / 设备`。

4. `异常信息要压缩成摘要`
   不把卡片做成报表，而是做成行动面板。

5. `同一页面允许差异化展示`
   不是每张卡都展示同样的字段，而是根据子状态动态强调。

## 4. 页面状态模型

### 4.1 一级状态

保留当前页面主 Tab 结构：

- `待审阅`
- `AI已驳回`
- `已派单`
- `待关闭`

本文档仅定义 `已派单` 页。

### 4.2 二级执行子状态

`已派单` 不是终态，而是一个执行阶段集合。建议在 `workflow_status = dispatched` 下增加衍生子状态 `execution_status`：

| execution_status | 中文 | 含义 |
|------------------|------|------|
| `pending_accept` | 待接单 | 已派给责任人，但尚未确认接单 |
| `accepted` | 已接单 | 已确认接单，但未到场 |
| `arrived` | 已到场 | 已到现场，开始排查 |
| `processing` | 处理中 | 已明确进入处理动作 |
| `waiting_support` | 待协同 | 卡在跨班组/跨系统/配件/厂商支持 |
| `overdue` | 已超时 | 超过 SLA 节点但未完成当前动作 |

### 4.3 子状态的生成规则

建议 `execution_status` 由后端根据时间字段和标记字段衍生，不直接替代主状态。

推荐规则：

1. `assigned_at` 有值，`accepted_at` 为空，且当前时间 <= `sla_due_at` -> `pending_accept`
2. `accepted_at` 有值，`arrived_at` 为空 -> `accepted`
3. `arrived_at` 有值，`processing_started_at` 为空 -> `arrived`
4. `processing_started_at` 有值，`waiting_support` 为 false -> `processing`
5. `waiting_support` 为 true -> `waiting_support`
6. 当前时间 > 当前阶段 `sla_due_at` 且未关闭 -> `overdue`

### 4.4 为什么不把子状态直接写进主状态机

原因有三点：

1. 主状态机承载业务流转，不宜过于细碎。
2. 子状态更多服务 `UI 展示` 与 `SLA 管控`。
3. 同一主状态下仍需要更多进度感知，这是运维页面的核心价值。

## 5. 页面目标与用户任务

### 5.1 主要用户

- 运维经理 / 能耗主管
- 值班调度人员
- 高级运维工程师

### 5.2 页面核心任务

用户打开 `已派单` 页时，通常要完成以下任务：

1. 快速识别 `超时或临期` 工单。
2. 找出 `仍在持续异常` 的高风险工单。
3. 判断 `责任是否落实`。
4. 催办、联系或升级处理。
5. 必要时查看趋势和详情做复核。

因此，页面的默认排序、筛选和卡片结构，都应服务这五个任务。

## 6. 已派单页面信息架构

### 6.1 页面结构

建议页面结构如下：

```text
页面标题：工单审阅
一级 Tab：待审阅 | AI已驳回 | 已派单 | 待关闭
二级摘要栏：总数 / 已超时 / 临期 / 持续异常 / 重复故障
筛选栏：项目 | 楼栋 | 系统 | 子状态 | 责任人 | 是否超时
列表区：状态驱动卡片
底部固定操作：TabBar
```

### 6.2 已派单页的摘要栏

推荐在列表上方新增一行摘要指标，而不是只显示“共 X 条”。

建议字段：

| 指标 | 说明 |
|------|------|
| `已派单总数` | 当前 Tab 全量 |
| `已超时` | execution_status = overdue |
| `30分钟内临期` | SLA 剩余 <= 30min |
| `持续异常` | is_active = true |
| `近7天重复` | repeat_count_7d >= 3 |

这行摘要能帮助值班人员先看风险分布，再下滑查看卡片。

## 7. 卡片信息架构

### 7.1 卡片统一骨架

建议卡片拆成 6 个区块：

1. `状态头部`
2. `对象定位`
3. `异常摘要`
4. `工单推进`
5. `影响与建议`
6. `快捷操作`

### 7.2 区块 A：状态头部

这是卡片最重要的区域，必须放在最顶部。

建议展示字段：

- `优先级`
- `异常类型`
- `执行子状态`
- `SLA 倒计时 / 超时提示`

推荐 UI 形式：

- 左侧为 2 个胶囊标签：`高优先`、`空调耗能`
- 右侧为状态标签：`待接单`
- 状态标签右边或下一行显示倒计时：`18 分钟后超时`

推荐文案示例：

- `高优先 | 空调耗能 | 待接单 | 18分钟后超时`
- `高优先 | 空调耗能 | 处理中 | 已超时 26 分钟`
- `中优先 | 照明耗能 | 待协同 | 等待弱电班组回复`

### 7.3 区块 B：对象定位

用于告诉用户“问题具体在哪儿”。

建议展示格式：

`项目 / 楼栋 / 楼层 / 系统 / 设备`

最少展示到：

- `楼栋`
- `楼层`
- `系统`
- `设备`

附加字段：

- `事件编号`
- `工单编号`

推荐示例：

```text
公共服务楼 / 3F / 空调系统 / AHU-02
事件编号 INC-20260311-001    工单编号 WO-20260311-023
```

### 7.4 区块 C：异常摘要

这部分要压缩成可读性很强的一行或两行摘要，不建议拆成太多零散小卡片。

建议核心字段：

- `当前值`
- `基线值`
- `偏差率`
- `持续时长`
- `连续次数`
- `当前是否仍异常`

推荐展示方式：

```text
当前 53.8，基线 11.7，偏差 +454.8%，已持续 60 分钟，连续 2 次，当前仍异常
```

次级信息：

- `首次发现`
- `最近异常`
- `近7天重复次数`

在视觉上建议把 `当前仍异常 / 已恢复 / 波动中` 做成单独状态点，而不是埋在段落中。

### 7.5 区块 D：工单推进

这是 `已派单` 页最核心的模块，权重应高于 AI 分析。

建议字段：

- `责任人`
- `班组`
- `联系电话`
- `派单时间`
- `接单时间`
- `到场时间`
- `最新进度`
- `预计完成时间`

推荐展示结构：

```text
责任人：张强（暖通班）  138****6621
派单：03-11 05:03   接单：03-11 05:12   到场：03-11 05:29
最新进度：已到现场，正在检查时段策略与阀门反馈
预计完成：03-11 06:20
```

如果字段过多，可以将 `联系方式` 放入按钮 `联系责任人`，但 `责任人 + 班组 + 派单/接单状态` 不能隐藏。

### 7.6 区块 E：影响与建议

这部分要从“描述文字”改成“行动辅助信息”。

建议字段：

- `影响评估`
- `AI 原因 Top3`
- `建议首查动作`
- `风险提示`

推荐结构化展示：

```text
影响评估：预计本时段多耗电 86 kWh，约增加费用 73 元，影响 3F 办公区舒适度
可能原因：时段策略失效 / 阀门卡滞 / 送风温度点位漂移
建议首查：排班策略 -> 阀门反馈 -> 送风温度
风险提示：异常仍持续，建议 30 分钟内完成现场确认
```

不建议继续只使用一段长篇 AI 描述。

### 7.7 区块 F：快捷操作

建议底部固定 4 个操作按钮：

- `趋势`
- `联系`
- `催办`
- `详情`

说明：

- `趋势`：查看近 24 小时趋势和期望对比
- `联系`：拨打责任人电话或发消息
- `催办`：发送催办提醒
- `详情`：进入完整工单页

如果产品上允许，也可以在超时工单上增加 `升级` 操作。

## 8. 子状态驱动的显示策略

不同子状态下，卡片重点字段要变化。建议如下：

| 子状态 | 必须重点显示 | 次要显示 | 可折叠/降低权重 |
|------|--------------|----------|----------------|
| 待接单 | 责任人、派单时间、接单倒计时、联系电话、是否仍异常 | 异常摘要、AI原因 | 预计完成时间 |
| 已接单 | 接单时间、预计到场时间、责任人、当前位置反馈 | 异常摘要、影响评估 | 重复故障信息 |
| 已到场 | 到场时间、最新检查点、是否仍异常 | 原因Top3、趋势入口 | 联系方式 |
| 处理中 | 最新进度、预计完成时间、影响评估、是否超时 | 异常摘要、AI建议 | 连续次数 |
| 待协同 | 等待对象、等待事项、等待时长、卡点原因 | 异常摘要、影响评估 | AI建议 |
| 已超时 | 超时多久、责任人、最新进度、催办/升级入口、是否仍异常 | 影响评估 | 一般性说明文字 |

### 8.1 待接单卡片重点

运维管理者此时最关心：`谁还没接单`、`多久超时`。

推荐强化样式：

- `接单倒计时` 用橙色/红色高亮
- `联系` 和 `催办` 按钮前置
- `最新进度` 直接显示 `尚未接单`

### 8.2 处理中卡片重点

此时应突出：`处理是否在推进`、`异常是否已下降`、`还需多久`。

推荐强化样式：

- `最新进度` 占两行
- 如果异常已恢复但工单未关闭，显示 `已恢复，待现场确认`
- `趋势` 按钮优先级上升

### 8.3 待协同卡片重点

这类卡片本质上是协同管理卡片，不再只是维修卡片。

必须显示：

- `等待对象`
- `等待事项`
- `等待时长`
- `当前卡点`

文案示例：

`等待对象：弱电班组`

`等待事项：核查 BMS 时段策略下发状态`

`等待时长：42 分钟`

### 8.4 已超时卡片重点

已超时卡片应该在视觉和排序上最先被关注。

规则：

1. 顶部状态标签改为红色：`已超时 26 分钟`
2. 卡片边框增加弱红色高亮
3. `催办` 按钮升级为主按钮
4. 若持续异常且高优先，显示 `建议升级` 提示

## 10. 视觉设计建议

### 10.1 整体风格

建议延续当前页面的浅色运营风格，但把风险层级做得更清晰。

推荐风格：

- 页面背景：浅灰蓝渐变底
- 卡片背景：白色到极浅蓝的轻渐变
- 卡片圆角：`24rpx - 28rpx`
- 卡片内边距：`24rpx - 28rpx`
- 模块分割：浅色细边框 + 12rpx 间距

### 10.2 状态色建议

| 类型 | 颜色建议 | 说明 |
|------|----------|------|
| 高优先 | 红橙系 | 表示风险高 |
| 中优先 | 橙色 | 表示关注 |
| 低优先 | 绿色 | 表示一般 |
| 待接单 | 蓝色 | 表示等待动作 |
| 处理中 | 蓝绿色 | 表示推进中 |
| 待协同 | 紫灰蓝 | 表示等待外部依赖 |
| 临期 | 橙色 | 表示临近 SLA |
| 已超时 | 红色 | 强风险提示 |
| 已恢复 | 绿色点标 | 告诉用户异常已缓解 |

## 12. 显示规则

### 12.1 标签规则

1. `is_active = true` 显示 `仍异常`
2. `is_active = false` 且工单未关闭，显示 `已恢复，待确认`
3. `repeat_count_7d >= 3` 显示 `重复异常`
4. `impact_energy_kwh` 或 `impact_cost` 超过阈值，显示 `高影响`

### 12.2 SLA 规则

1. `剩余 > 30 分钟`：默认蓝灰色
2. `剩余 <= 30 分钟`：橙色高亮，文案 `30分钟内临期`
3. `剩余 <= 10 分钟`：橙红色高亮，文案 `10分钟内超时`
4. `已超时`：红色，文案 `已超时 X 分钟`

### 12.3 异常摘要规则

推荐按以下格式拼装：

`当前 {actual}，基线 {expected}，偏差 {deviation}，持续 {duration}，连续 {count} 次`

如果 `actual/expected` 缺失，则退化为：

`峰值偏差 {peak_deviation_pct}，持续 {duration}，连续 {count} 次`

### 12.4 AI 建议规则

1. `ai_root_causes` 最多展示 3 条
2. `recommended_checks` 最多展示 3 步
3. 文案以短句为主，不超过 28 字/项

## 16. 验收标准

如果本方案落地，`已派单` 页面至少应满足以下验收标准：

1. 用户在不进入详情的情况下，能在 3 秒内判断：
   `谁在处理、是否超时、异常是否还在`

2. 用户在首屏就能区分：
   `待接单`、`处理中`、`待协同`、`已超时`

3. 卡片中的 AI 内容不再喧宾夺主，而是作为辅助建议存在。

4. 超时工单在视觉和排序上明显优先。

5. 卡片中的对象定位足以支持一线运维直接派工。

6. 页面支持值班场景下的高频操作：
   `趋势`、`联系`、`催办`、`详情`

## 17. 结论

`已派单` 页最需要解决的问题，不是补充更多异常信息，而是建立围绕 `工单状态` 的展示秩序。

最终推荐方案为：

1. 保留现有一级 Tab。
2. 在 `已派单` 下引入 `execution_status` 子状态。
3. 使用 `统一骨架 + 状态驱动权重变化` 的卡片结构。
4. 让 `工单推进线` 成为该页面第一优先级。
5. 把 AI 说明从长文本改为 `原因 Top3 + 建议首查动作`。

这样改造后，页面才能真正从“异常列表”升级为“运维调度面板”。
