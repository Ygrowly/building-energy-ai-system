### 数据库设计核心理念
由于环境限制无法使用 TimescaleDB，我们回归到原生 PostgreSQL 的最佳实践，方案核心围绕以下三大理念构建：

1. **“物数分离”的规范化设计**：依然严格遵循将建筑物的静态“物”属性与动态的“数”流进行解耦的工业级设计原则，确保了数据模型的高度内聚与低耦合。
2. **索引驱动的性能优化**：在无法依赖时序数据库自动分区的前提下，将查询性能的宝全部押在**高度定制化的索引**上，通过B-Tree索引结构加速关键业务场景的查询速度。
3. **“手动挡”的预聚合加速**：创造性地使用 PostgreSQL 的**物化视图（Materialized View）**来模拟 TimescaleDB 的连续聚合功能，为统计分析类查询提供“数据快照”，以空间换时间，极大提升了前端可视化的响应速度。

### 数据库表结构与特性详解
我们的数据库由**一张关系型表**、**一张时序数据表**和一个**物化视图**构成。

#### A. 基础信息表 (Relational) - `buildings`
+ **定位**：数字孪生世界的“**资产身份证**”。
+ **作用**：存储建筑物的静态元数据，作为所有数据的关联起点。
+ **表结构设计**：

```sql
CREATE TABLE buildings (
    building_id     TEXT PRIMARY KEY,       -- 建筑唯一ID (主键，使用 TEXT 兼容性更广)
    building_type   TEXT,                   -- 建筑类型
    meter_device_id TEXT UNIQUE NOT NULL,   -- 监测设备ID
    sqm             REAL                    -- 建筑面积
);
```

+ **索引策略**：在 `building_type` 上建立了索引，专门用于加速“按建筑类型筛选”的场景（例如：查询所有教学楼）。

#### B. 能耗时序表 (Time-Series) - `energy_data`
+ **定位**：系统的“**核心数据日志**”，按时间顺序记录所有监测和仿真数据。
+ **作用**：作为所有实时查询、明细查询和AI智能问答的数据源头。
+ **表结构设计**：

```sql
CREATE TABLE energy_data (
    "timestamp"                 TIMESTAMPTZ NOT NULL,  -- 监测时间 (依然保留了带时区的最佳实践)
    building_id                TEXT NOT NULL,         -- 关联 buildings 表
    electricity_kwh            REAL,
    water_m3                   REAL,
    hvac_energy_kwh            REAL,
    hvac_supply_temp_c         REAL,
    hvac_return_temp_c         REAL,
    ambient_temp_c             REAL,
    humidity_rh_pct             REAL,
    occupancy_density_per_100sqm REAL,
    operation_status           operation_status_enum  -- 运行状态 (使用自定义枚举类型，节省存储)
);
```

+ **核心索引策略（性能的关键）**：
    1. **复合索引 **`(building_id, "timestamp" DESC)`：这是整个方案的**“性能顶梁柱”**。它将同一栋楼的数据在物理上聚合在一起，并按时间倒序排列。当查询“某栋楼最近24小时的数据”时，数据库可以直接在这个索引的头部进行极小范围的扫描，**避免了全表扫描的灾难**。
    2. **单列索引 **`("timestamp")`：这是一个辅助索引，主要用于不区分建筑、只按时间范围进行全局聚合的场景（例如：“查询全校所有建筑在昨天中午12点的总用电量”）。

#### C. 每日汇总物化视图 - `daily_energy_summary`
+ **定位**：系统的“**性能加速缓存**”，是为统计报表量身定制的预计算结果集。
+ **作用**：专门应对前端大屏展示、月报/年报生成等需要按天进行聚合的重计算场景。
+ **视图结构**：

```sql
CREATE MATERIALIZED VIEW daily_energy_summary AS
SELECT
    date_trunc('day', "timestamp") AS day, -- 按天对时间进行截断
    building_id,
    SUM(electricity_kwh)              AS total_electricity_kwh,
    AVG(ambient_temp_c)             AS avg_ambient_temp,
    MAX(occupancy_density_per_100sqm) AS max_occupancy
FROM energy_data
GROUP BY day, building_id;
```

+ **运维要求（与TimescaleDB的主要区别）**：这是一个“手动挡”的缓存。数据写入 `energy_data` 后，这个视图**不会自动更新**。你必须在应用层面（例如：设置一个后台定时任务，每小时或每天凌晨）执行 `REFRESH MATERIALIZED VIEW CONCURRENTLY daily_energy_summary;` 来手动刷新它。`CONCURRENTLY` 关键字确保了刷新时不会锁表，不影响前端的正常读取。
+ **索引策略**：在 `(day, building_id)` 上创建了唯一索引，保证了查询这个聚合视图时的极速响应。

### 方案总结：为何这依然是一套高分企业级方案？
1. **结构规范**：完全遵循数据库设计范式，逻辑清晰，易于理解和扩展。
2. **性能导向**：虽然没有时序数据库的自动分区，但通过**精准的复合索引**和**创造性的物化视图**，最大限度地弥补了原生 PostgreSQL 在时序场景下的性能短板，确保了核心业务的流畅性。
3. **数据一致性**：通过在 `buildings` 表上设置 `UNIQUE` 约束，以及在应用层保证 `building_id` 的引用正确性，实现了“无外键”下的数据一致性。
4. **存储优化**：巧妙地使用了 `ENUM` 类型来存储“运行状态”，相比直接用 TEXT，每个字段能节约数个字节，在百万、千万级数据量下，积少成多。
