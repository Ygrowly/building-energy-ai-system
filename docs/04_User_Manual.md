## 1. 系统简介

### 1.1 系统定位

“绿枢智控”不是单一页面或者单一模型服务，而是一套围绕楼宇能耗运转起来的系统。它把结构化数据接入、查询统计、异常识别、预测预警、工单管理、派工执行、移动维修和知识经验沉淀放在同一条链路里。对使用者来说，最直接的感受应该是：它既能看到问题，也能继续处理问题。

### 1.2 角色与终端

系统当前主要有三类业务角色。

- `admin` 是系统管理员，更多从全局视角看系统、账号和流程。
- `manager` 是运维经理，重点在工单审阅、派工改派、执行跟踪和运营分析。
- `ops` 是维修人员，主要在移动维修端完成接单、到场、处理、协同和反馈。

终端入口也因此分成三块。Web 管理端运行在 `http://localhost:5173`，适合管理员和运维经理使用，PC 端 AI 对话助手“碳小能”也在这里使用；移动端 H5 常见地址是 `http://localhost:5174`，其中运维侧页面给 `admin`、`manager` 使用，并接入移动运维助手“运小维”，维修侧页面给 `ops` 使用，并接入现场维修助手“维小修”。三者不是彼此独立的新系统，而是挂在不同终端和不同角色流程里的 AI 能力入口。

## 2. 安装与部署步骤

### 2.1 先准备什么

在本地把项目跑起来，最少需要这些环境：Python 3.10 及以上、Node.js 18 及以上、pnpm 8 及以上、PostgreSQL 14 或 15、Redis 7 以及一套可访问的 RAGFlow 服务。目录方面，日常最常用的是 `backend/`、`frontend/`、`mobile/` 和 `backend/migrations/`。前面三个分别对应后端、Web 和移动端，最后一个负责数据库 schema。

这里有个容易误解的点：仓库里的 `docker compose up -d` 只会帮你把 Redis 起起来，不会顺便帮你把 PostgreSQL 和 RAGFlow 也装好。如果数据库和知识库环境没准备，这一步最多只能算“本地缓存准备完成”。

如果是第一次接手这个项目，建议先把目录看一遍再动手。很多部署问题不是命令写错了，而是把不同目录下的命令混着跑了。尤其是 `backend`、`frontend` 和 `mobile` 三个子项目各自都有依赖和启动命令，顺序一乱，后面排查起来会很费时间。

### 2.2 第一次启动建议按这个顺序

第一次在新机器上启动，建议别同时开太多窗口，按顺序做更稳。

1. 先准备 PostgreSQL、Redis 和 RAGFlow。
2. 再去配置 `backend/.env`，把数据库、缓存、模型和知识库连接项填对。
3. 把数据库 schema 初始化好，然后启动后端，先看 `/health` 和 `/health/db`。
4. 后端没问题以后，再起 Web 管理端。
5. 最后再起移动端 H5。
6. 三端都起来以后，再考虑导入数据和准备演示账号。

如果第三步没通过，后面就不要急着继续。很多“前端白屏”或者“页面没数据”的问题，根本原因其实都在后端和数据库没准备好。

这个顺序看起来有些保守，但它的好处是排查路径很短。每一步都只验证一层能力：先验证基础设施，再验证后端，再验证桌面端，再验证移动端。这样一旦有问题，基本能立刻知道问题停在哪一层，而不会出现所有服务都开了、却不知道是哪一层出错的情况。

### 2.3 后端部署

先安装依赖：

```powershell
cd backend
pip install -r requirements.txt
```

然后把 `backend/.env.example` 复制成 `backend/.env`。真正需要先确认的变量并不复杂，主要就是 `DATABASE_URL`、`SYNC_DATABASE_URL`、`REDIS_URL`、`LLM_API_KEY` 或 `DASHSCOPE_API_KEY`，以及 `RAGFLOW_API_URL`、`RAGFLOW_API_KEY`、`RAGFLOW_DATASET_ID`。另外还有 `DATA_TIME_START` 和 `DATA_TIME_END`，它们会影响默认演示时间范围。

Redis 可以在仓库根目录用下面的命令启动：

```powershell
docker compose up -d
```

后端启动命令如下：

```powershell
cd backend
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

启动以后，先别急着打开页面，先访问：

- `http://127.0.0.1:8000/health`
- `http://127.0.0.1:8000/health/db`

如果 `/health` 返回 `status: ok`，说明应用本身起来了；如果 `/health/db` 也返回 `status: ok` 和 `ping: 1`，说明数据库连接是通的。做到这里，后端才算真正准备完成。

除了健康检查，还建议留意终端日志。当前后端在启动时会输出 Redis 初始化、楼宇列表预加载、定时任务等信息，这些日志对判断系统是不是“真正进入工作状态”很有帮助。尤其是数据库 schema 兼容和视图初始化这类动作，虽然不一定每次都在页面可见，但日志通常能给出非常直接的提示。

### 2.4 前端部署

Web 管理端的启动方式很直接：

```powershell
cd frontend
pnpm install
pnpm dev
```

默认情况下，页面会跑在 `http://localhost:5173`。如果只是演示和联调，这一步够用了；如果需要构建产物，再额外执行一次 `pnpm build` 即可。

Web 端起起来以后，建议不要第一时间就去翻复杂模块，先看登录页和首页。如果连首页都打不开，说明问题通常还停留在最基础的接口联通层；如果首页能开，但某个业务页打不开，才更可能是具体模块的数据或者权限问题。

### 2.5 移动端 H5 启动

移动端命令也比较简单：

```powershell
cd mobile
pnpm install
pnpm dev:h5
```

常见端口是 `5174`，但如果本机端口占用，终端可能会自动换一个。这里不要死记端口号，以命令行实际输出为准。

移动端的联调建议放在 Web 端之后做。因为移动端虽然入口不同，但底层仍然依赖同一套后端。如果后端和 Web 端还没跑顺，过早去查移动端问题，往往只是在放大同一个底层错误。

### 2.6 PostgreSQL、Redis 和 RAGFlow 各自负责什么

PostgreSQL 是系统的主数据库，建筑、设备、能耗、异常、预测、工单、派工和经验数据都在里面。Redis 主要负责缓存高频查询结果，比如首页概览和工单列表；Redis 异常不会让系统彻底不可用，但页面可能会变慢。RAGFlow 则只影响知识库上传、解析和部分 AI 检索能力，不会影响结构化数据查询和工单主流程。

也就是说，如果你只是做页面演示、数据查询和派工闭环，RAGFlow 暂时没就绪其实不至于卡死；但如果要完整使用文档知识库，以及碳小能、运小维、维小修在知识检索上的增强能力，就必须提前准备好。

### 2.7 数据库初始化和演示数据导入

#### 2.7.1 数据库怎么初始化

这个仓库当前没有专门的一键初始化脚本，数据库结构以 `backend/migrations/` 目录下的 SQL 文件为准。实际做法通常是：

1. 先在 PostgreSQL 里创建业务数据库。
2. 按文件名前缀顺序执行迁移 SQL。
3. 启动后端，让应用在启动阶段补齐兼容字段、AI 相关表、通知表、经验表和 `daily_energy_summary` 物化视图。

需要特别说明的是，`dataset/import_script.py` 和 `dataset/simulation_engine/` 现在还是占位文件，不能指望它们替你完成数据库初始化。所以如果是第一次部署，还是要走迁移 SQL 这条路。

执行迁移时，最稳妥的做法是保留一个执行记录，至少知道自己跑到了哪一份 SQL。因为当前迁移文件较多，而且中间有几次 schema 演进是围绕工单、派工、AI 和通知逐步加上去的。如果中途失败但没有记录，后续很容易出现“表看起来在，但字段不全”的半初始化状态。

#### 2.7.2 演示数据怎么导入

项目当前没有固定写死在仓库里的成品演示 CSV 路径，实际演示一般有三种做法。第一种是直接使用已有数据库中的样本；第二种是提前准备标准化 CSV 或 Excel，然后通过 Web 数据中心上传导入；第三种是参考 `docs` 里的 notebook 生成样本后再导入。

Web 导入流程本身不复杂。进入“数据中心”后，先上传 `.csv`、`.xlsx` 或 `.xls` 文件，系统会先分析列名、样本和统计信息。确认无误以后，再点击“导入到 `energy_data`”。导入过程中页面会收到 SSE 进度，最后能看到 `imported_rows`、`failed_rows`、`building_ids`、`min_ts`、`max_ts` 这些结果。看到这些信息，再去查询统计页验证对应楼宇和时间段能否查到数据，这样比较稳。

这里有几个容易忽略的检查点。第一，确认时间列和楼宇列是否真的被识别到了，而不是被错误地映射成别的字段。第二，确认导入时间范围和你准备演示的时间范围一致。第三，确认 `invalid_building_ids` 是否为空。如果这一步没看，后面到了查询统计页发现“只有一部分数据”，往往还要再回头查一次导入结果。

### 2.8 演示账号说明

如果已经执行过仓库里的辅助脚本，当前比较常用的联调账号有：

- `test1 / test1234`，用于运维经理或调度演示。
- `ops_hvac_01 / test1234`，适合 HVAC 相关工单。
- `ops_electrical_01 / test1234`，适合电力相关工单。
- `ops_plumbing_01 / test1234`，适合给排水相关工单。
- `ops_controls_01 / test1234`，适合控制类工单。
- `ops_general_02 / test1234`，适合通用维修工单。

如果当前数据库里没有这些账号，可以在 `backend/` 目录执行：

```powershell

```

正式答辩时，如果不想在材料里直接写密码，可以把这里改成“演示账号由部署环境统一准备”。但从仓库现状来说，这些示例账号确实是存在脚本支撑的，不是文档凭空写出来的。

### 2.9 登录验证

部署完成后，建议先用 `test1` 登录 Web 管理端，确认首页、数据中心、查询统计和工单管理都能正常打开。接着再打开移动端 H5，用 `test1` 验证运维侧页面，用 `ops_hvac_01` 之类的账号验证维修侧页面和维小修入口。这里的目的不是把每个按钮都点一遍，而是确认三类入口和三类角色都已经打通。

如果要做一个最小化冒烟测试，实际上只要确认四件事：能登录、首页能看到数据、工单页能打开、移动维修端能进入某张工单详情。只要这四步都通了，说明系统主链路已经基本可用，后续再去补知识库和 AI 细节会轻松很多。

## 3. Web 管理端操作流程

### 3.1 首页总览

登录之后，系统默认进入首页。首页适合做第一次演示，因为这里能把项目的主线一下子讲出来：上方是日期、天气和消息入口，中间是 KPI 卡片，下面可以切换总览、教学楼、办公楼和公共服务楼三种视角。评委如果先看这里，基本就能知道系统既做了统计展示，也做了异常和预警。

这里的切换逻辑其实对应了两层分析口径。总览视角更偏平台整体运行情况，适合先看当前有没有明显异常、哪一类风险最值得关注；切到教学楼、办公楼或公共服务楼以后，页面就更接近建筑专属分析，适合继续看某一类建筑的波动特征和异常差异。

正常情况下，首页加载成功后能看到 KPI、异常概况、预测预警和 AI 洞察。如果页面打开但一片空白，或者所有指标都是空值，优先检查后端接口和数据库，不要一开始就去前端找样式问题。

从演示节奏上说，首页也很适合作为开场页。因为这里同时展示了数据、异常、预测和消息入口，能够在很短时间里把“这不是一个单纯看图的系统”表达出来。相比一上来就进数据中心或某个细节页面，首页更适合先建立整体印象。

### 3.2 数据中心

数据中心是整个系统里最“入口型”的模块。结构化数据和知识库文档都从这里进入系统。

如果要导入结构化样本，进入“数据集”页签以后先上传文件，先看列映射和样本预览，再决定要不要导入。这个顺序别反过来，否则很容易把口径没对齐的数据直接写进库里。导入过程中会有进度反馈，导入完成以后页面会显示行数、失败数和无效楼宇列表。看到这些结果，再去查询统计页验证，就能确认数据已经真正进入业务链路。

如果要上传知识库文档，则切到“知识库”页签，上传 PDF、Word、TXT 或 Markdown 文档后触发解析。这里最容易踩的坑是 RAGFlow 没配好。一旦知识库解析失败，先查 RAGFlow 连接，不用先怀疑前端。

数据中心这一页在答辩里还有一个作用，就是说明项目不是拿固定假数据硬写页面。只要演示一次上传、预览和导入，就能让人明白系统对数据入口是有真实处理能力的。相比单纯说“我们支持导入”，现场演示一下导入前预览和导入后校验，可信度会高很多。

### 3.3 查询统计

查询统计页适合展示系统对结构化数据的掌控能力。进入以后，先选建筑类型，再选时间范围，再决定看哪些指标。正常演示时，不建议一次把时间拉得太长，7 天到 30 天之间通常最合适，既能看出趋势，也不至于让图表太密。

查询成功以后，页面会显示趋势图、统计信息和明细表。如果开启了实际值对比或异常分析，还能看到异常时段和结论说明。这里的价值在于，它不是只给出“有问题”，而是尽量把“问题表现在哪里”说清楚。

如果当前结果需要留存，查询统计页本身也可以作为报表整理的起点。一种做法是直接使用页面导出能力拿结构化结果，另一种做法是把当前页面结果继续交给碳小能整理成带结论的对话报表。前者更适合数据复核，后者更适合把图表和分析说明一起留存。

如果是第一次演示，建议先选一栋楼、一个较短时间窗口和两三个最关键的指标。这样图会比较干净，结论也容易讲。等把基本趋势讲清楚以后，再切到实际值对比或者异常时段说明，逻辑会更顺。很多演示一上来就选太多指标，结果图上信息太满，反而讲不清重点。

### 3.4 智慧运维与碳小能

智慧运维相关内容目前主要落在首页异常区块和右侧 AI 控制台里。页面本身会展示近期异常和预测预警，而 PC 端的碳小能则负责把这些结构化结果进一步组织成可追问、可解释的分析过程。这里更适合提一些真实管理问题，比如“最近 7 天办公楼异常主要集中在哪些时段”“哪些工单已经超时”“本周哪个班组处理任务最多”“这一段夜间高耗和哪些工单有关联”。这样的提问方式比泛泛地问一句“系统能干嘛”更容易体现它的价值。

需要注意的是，碳小能虽然能在分析过程中给出图表、证据链、报表入口，甚至生成待审批的工单建议，但它并不会绕过正式流程直接完成审批、改派或关闭工单。所以如果问它“帮我把这张工单直接改派掉”，当前设计下它最多会给出依据、候选方向或待确认卡片，真正改动数据仍然要回到正式业务页面。这一点是刻意保留的人机边界。

实际使用时，碳小能更适合用来做三类问题。第一类是“当前发生了什么”，比如近期异常和超时工单；第二类是“为什么会这样”，比如某类异常为何集中在某栋楼或某个时段；第三类是“下一步该看什么”，也就是让它给出后续核查建议。只要围绕这三类问题来问，返回结果通常都比较稳定。

从交互形式上看，AI 控制台也不是一次性整段返回。Web 端通常会先显示思考中的状态，再陆续显示文字、图表卡片、工单卡片或报表下载卡片。如果问题更复杂，可以切到更深的思考模式；如果当前分析结果需要留存，也可以直接从对话侧导出对话报表，不必再手工整理一遍页面结果。当前页面还支持把正在看的图表或指标区域作为上下文带进对话里，因此碳小能并不只是回答抽象问题，也适合接着当前页面继续解释。

### 3.5 工单管理

工单管理是 Web 端里最接近业务闭环的模块。项目当前把它拆成审阅、派工和执行跟踪三个视角，这样讲起来比在一个页面里混着讲清楚得多。

在工单审阅里，主要看待审工单和 AI 给出的建议理由。这里做的是“要不要进入维修流程”的判断。通过以后，工单进入待派工；驳回以后，则会进入驳回态，不再继续往下走。

到了派工中心，关注点就变成了“应该派给谁”。系统会给出候选维修人员、技能匹配和推荐理由。选完责任人以后，工单主状态会变成 `dispatched`，而对应的派工任务则开始进入 `pending_accept`。这两个状态是一起看的，不要混在一起理解。

执行跟踪页则是管理端盯现场进度的地方。这里能看到任务是待接单、已接单、已到场、处理中、待协同还是已超时。到了这一步，工单已经不再是“有没有问题”的抽象问题，而是“现场处理到了哪一步”的具体问题。

这三个视角建议分开理解。审阅解决的是“要不要处理”，派工解决的是“谁来处理”，执行跟踪解决的是“处理到哪了”。很多人第一次看这个模块时会觉得页面有点多，其实是因为系统故意把不同阶段拆开了，避免把审批、调度和现场状态混在同一张列表里。

除了这三条主线，当前工单区还承接工单大厅和自动重派相关事项。当任务需要共享协同、已经超时待接管，或者系统给出自动重派影子评估时，管理端不只是看一张普通工单，而是要继续处理申请记录、接管候选人和只读评估结果。可以把这部分理解为“常规派工之外的二次调度层”。

这里尤其要注意，自动重派并不是所有工单都会直接执行。当前页面里会先展示只读评估、影子观察或灰度相关信息，作用是帮助管理者判断这张单是否值得改派、是否存在更合适人选，而不是让系统在没有边界的情况下自动改动正式责任人。

### 3.6 人员画像

人员画像模块不是单纯的人事信息页，它直接影响派工推荐结果。这里可以维护班组、技能、值班状态、是否允许派工以及最大在手工单数。改完以后，派工中心的推荐会随之变化。

如果答辩时要讲“智能派工不是随机派”，这里就是最合适的落点。因为它可以把推荐背后的人员约束说清楚，而不是只展示一个派工结果。

在实际联调里，这个模块也很适合做问题回溯。比如某张工单为什么会被派给某位维修人员，或者为什么某位人员没有出现在候选列表里，通常都可以从技能、班组、值班状态和在手任务数这些画像信息里找到解释。

### 3.7 消息中心与个人中心

消息入口在首页右上角铃铛和个人中心里。这里主要承接待处理消息、近期异常提醒和角色权限说明。虽然它不是系统最核心的业务模块，但在演示时很有用，因为它能让页面显得像一个正在运行的系统，而不是静态样板。

如果是做完整演示，这里可以顺手点开看一下未处理提醒和个人信息，不需要停留太久，但能起到两个作用。第一，它能说明系统不是只有大模块，日常通知和个人入口也已经接进来了；第二，它也方便自然过渡到工单、消息和角色权限这些后续内容，让演示节奏更顺一些。

## 4. 移动运维端操作流程

### 4.1 登录

移动运维端给 `admin` 和 `manager` 使用。登录以后，通常会先进入总览或工单相关页面。这里建议直接用 `test1` 演示，因为它和 Web 管理端的角色一致，前后讲起来比较顺。

### 4.2 总览与消息

运维端总览页适合看待处理工单、异常提醒和一些简化过的运行信息。它不是把 Web 首页原样搬过来，而是保留了管理者在手机上最关心的内容。消息页则更适合快速查看提醒，不需要每次都回到桌面端。

这里最好把移动端的定位讲清楚：它更像“补位终端”，不是把桌面端所有分析能力压缩进手机里。也正因为如此，页面保留的是最需要随手处理的内容，而不是所有图表和明细。这种取舍不是功能缺失，而是移动场景本来就更强调速度和可达性。

图 4-1 移动运维端总览页（截图位，答辩版建议替换为真实运行截图）

### 4.3 工单审阅

运维侧在手机上也可以做工单审阅。进入工单审阅页以后，可以先看待审、待派工和已派单这几类任务，再点开某张工单看 AI 理由和上下文。移动端的优势不是替代桌面端做所有细节，而是在“随手处理一下”这件事上更方便。

这类移动端操作在真实场景里很有意义，因为调度和审批不一定总发生在固定工位上。项目把这部分能力放到手机端，本质上是在强调“管理动作也可以在流程中完成”，而不是一定要回到桌面端才行。

### 4.4 派工与改派

待派工工单进入以后，流程和 Web 端是一致的：先看候选人，再看推荐理由，最后确认派工。如果责任人不合适，也可以从这里改派。实际演示时，这一段可以和人员画像配合着讲，效果会更完整。

如果现场网络或环境受限，移动端派工页其实也是一个很好的“轻量演示页”。它没有桌面端那么多辅助信息，但恰好能把核心动作压缩到几步之内，更适合展示系统在移动场景下的可用性。

如果这张工单已经进入共享协同或超时待接管阶段，移动运维端还会碰到工单大厅申请处理。这时候关注点就不只是“派给谁”，还包括“为什么进入大厅”“申请人想协同还是接管”“当前是否应该正式改派”。它本质上是二次调度，不是普通派工的重复。

### 4.5 执行跟踪与运小维

移动运维端还能直接跟踪现场执行状态。你能看到任务当前是在 `pending_accept`、`accepted`、`arrived`、`processing`、`waiting_support` 还是 `overdue`。如果想临时了解一段时间内的工单分布、超时原因、协同记录或接管情况，也可以直接通过运小维发起只读问询，不一定非得回到 Web 端。和 PC 端的碳小能相比，运小维更聚焦工单过程、班组负载和移动管理场景，而不是承担完整的数据中枢角色。

实际使用时，这一页很适合回答两类临时问题。第一类是“人在哪一步卡住了”，比如已经派出但一直没人接单；第二类是“最近哪里最忙”，比如某一类工单为什么总在超时。前者直接看状态流转，后者可以配合运小维做一个简短问询，这样移动端就不只是消息查看器，而是真的能承担一部分过程管理。对于不在电脑前的运维经理来说，这一点很关键，因为它让移动端不再只是审批入口，而是具备了简化版的过程分析能力。

## 5. 移动维修端操作流程

### 5.1 登录

移动维修端只给 `ops` 使用。答辩演示时通常用 `ops_hvac_01` 就够了，因为它最适合配合 HVAC 异常工单讲完整个处理链路。

### 5.2 工作台、我的工单和工单大厅

维修端最常用的不是某一张总览图，而是工作台和我的工单。工作台用来快速看今日任务和提醒，我的工单用来进正式分配给自己的任务，工单大厅则更适合看共享协同或可接管的任务。这里的设计思路很务实：先让维修人员知道“我现在该看哪张单”，而不是让他先看大量统计。

从使用习惯来看，这种设计比把所有任务混在一张列表里更适合现场。维修人员通常不会先关心复杂统计，而是先关心自己当前要处理哪一张单、有没有超时、有没有协同请求。工作台、我的工单和工单大厅这三个入口，刚好对应了这三种最常见的工作起点。

这里的工单大厅不是普通列表的另一个名字，而是专门承接共享协同和超时待接管事项的入口。维修人员可以在这里查看自己可申请的共享任务，提交协同或接管申请；只有在管理员确认之后，这些共享事项才会正式落到个人处理链上。

图 5-1 移动维修端工单详情页（截图位，答辩版建议替换为真实运行截图）

### 5.3 接单、到场、开始处理

维修端的标准动作非常清楚：先接单，再到场，再开始处理。动作不多，但每一步都对应状态变化。接单以后，任务从 `pending_accept` 进入 `accepted`；到场以后进入 `arrived`；正式开始处理以后进入 `processing`。这几步是整个执行链里最重要的骨架，答辩时只要把这条线讲顺，后面的协同和反馈就容易理解了。

这里建议在联调时顺手确认一下时间线是否有记录更新。因为对管理端来说，维修端动作不仅是状态切换，也是后续追踪和复盘的依据。如果现场动作都做了，但时间线没有更新，就说明链路还没有完全打通。

### 5.4 协同处理

如果一张单靠当前维修人员处理不了，可以从工单详情里发起协同请求。协同完成前，任务可能会进入 `waiting_support`。这一段设计的意义在于，系统没有假设每张单都能一次性独立处理完，而是把现实里常见的跨班组协同也留出了位置。

答辩时如果想把这一段讲得更真实，不妨直接说明什么情况下会触发协同。比如现场判断已经超出当前工种能力、需要控制类人员配合，或者需要另一班组协助排查电气与暖通的交叉问题。把协同写进系统，等于承认了维修流程本来就不是永远单人闭环，这会让整套流程显得更可信。

### 5.5 维小修怎么用

维小修不是一个泛聊天窗口，而是围绕工单上下文工作的维修助手。通常在工单已经进入处理阶段以后，页面会提供维小修入口。进来之后可以看到工单摘要和步骤卡片，也可以通过文字、语音和图片继续补充现场信息。

这里最值得讲的是步骤卡片。它不是简单给一段长文本，而是把处理过程拆成可推进、可更新状态的步骤。当前支持的状态包括 `pending`、`completed`、`skipped`、`needs_support` 和 `uncertain`。这让维小修更像现场辅助，而不是单次问答。

实际使用时，可以把维小修理解成“围绕当前工单工作的助手”，而不是“什么都能问的总助手”。越是围绕当前工单、当前现场和当前步骤去提问，返回内容越有价值。比如上传现场图片、补充当前现象、说明已经排查过哪些步骤，这些都会比泛泛地问一句“怎么修”更有效。

### 5.6 提交维修反馈与经验

处理完成以后，维修人员需要提交结果。当前结果口径包括 `fixed`、`false_alarm`、`escalated` 和 `needs_parts`。同时还可以填写备注、说明处理过程，并把可复用经验沉淀下来。

## 6. AI 助手使用说明

### 6.1 碳小能

碳小能是 PC 管理端的 AI 分析中枢，更适合做跨页面、跨指标和跨流程的综合分析。比如问最近 7 天异常集中在哪些时段，哪些工单已经超时，哪个班组最近处理量最多，或者这段异常和哪些待处理工单关联最强，这些都比较适合它。它的价值不是替代页面，而是把页面里分散的信息重新组织成一个更容易追问、复核和留存的分析过程。

比较推荐的提问方式是“对象 + 时间 + 问题”。例如“办公楼最近 7 天异常主要集中在哪些时段”“本周超时工单主要来自哪个班组”。这样的问题范围比较清晰，返回结果通常也更聚焦。如果只问“系统最近怎么样”，回答往往会偏泛。

如果在 Web 管理端使用，碳小能的对话通常会伴随流式思考提示、图表卡片、证据信息、工单卡片和报表入口返回。也就是说，它给出的不只是结论句子，还可能直接附带趋势图、指标卡、待确认工单建议或导出材料。对管理者来说，这种返回方式比单纯一段长文本更容易继续核查和留存。

### 6.2 运小维

运小维适合做移动运维侧的只读分析，尤其适合工单过程问题和调度回溯问题。比如问当前有哪些超时工单、哪一类协同申请最近增加、哪个班组本周处理量最高、某张工单为什么进入共享大厅，这些都比较适合它。它的价值不在于替代 PC 端的完整分析，而在于让管理角色在手机上也能迅速把工单过程看明白。

和碳小能相比，运小维更少去做大范围的能耗全景分析，更强调工单、派工、协同、接管和周期对比这类移动端高频管理问题。也正因为如此，它的表达会更贴近流程语言，比如直接说明某张单停在哪个环节、推荐先看哪一类申请、哪些事项最值得优先跟进。

### 6.3 维小修

维小修适合做现场指导。对维修人员来说，它最有用的地方不是“回答很长”，而是它能围绕当前工单给出步骤建议，必要时还能结合图片、语音和播报能力，让现场操作更顺。

如果现场环境不方便打字，语音转写和 TTS 的价值会更明显。尤其是在设备间或机房这类不适合长时间盯手机的环境里，让维小修把步骤播报出来，往往比让维修人员自己来回翻看说明更实用。

另外，维小修的步骤计划和历史对话都和具体工单绑定。进入同一张工单时，系统会继续读取已有步骤卡和历史记录，而不是每次从零开始，这对分多次处理、跨班次交接或协同处理中的连续排查都很重要。

### 6.4 人工和助手的边界

这三个助手都不是来替代角色本身的。碳小能可以给出分析、图表、证据和待审批建议，但不直接代替人完成正式审批和改派；运小维不直接审批或改派；维小修不直接越权修改工单结果。AI 给出的是建议、解释和辅助信息，真正落到业务数据上的动作，仍然要通过正式页面和接口来完成。这一点如果讲清楚，整套系统的边界会更稳，也更符合真实业务。

从使用角度看，也可以把边界理解成一句更简单的话：需要留痕、需要负责、会改变正式状态的动作，还是交给人；需要归纳、解释、提示和辅助判断的动作，再交给助手。这样一来，AI 的价值不会被夸大，但它在流程里的位置反而更清楚。

## 7. 常见问题排查

### 7.1 后端起不来

先检查 `backend/.env`，再检查数据库和 Redis，再看 `/health` 和 `/health/db`。如果数据库没有通，后面的页面问题基本都是连带问题，先别急着查前端。

如果后端能启动但页面没数据，也不要立刻把问题归到前端。先看健康检查，再看数据库有没有样本，再看默认时间范围是不是和样本时间对不上。很多“接口正常但页面空”的问题，本质上都是数据窗口没有对齐。

### 7.2 前端白屏或者接口 401

先确认后端是不是还活着，端口是不是还是 `8000`。如果是 401，先清空登录状态重新登录。很多时候不是权限逻辑有问题，而是本地 token 过期或者旧地址还缓存着。

如果只是个别页面白屏，而不是整个系统都白屏，建议顺手看一下浏览器网络请求。重点确认接口是不是已经发出、返回的是 401 还是 404、请求地址是不是还指向旧端口。把这些基础信息先看清楚，通常比一上来就改前端代码更有效。

### 7.3 端口冲突

`8000`、`5173`、`5174` 是最常见的三个端口。谁被占用了就改谁，但改完以后别忘了同步检查访问地址和代理配置。这个问题很常见，但也最容易因为粗心浪费时间。

### 7.4 CORS 或 token 失效

开发环境下，后端已经对常见本地端口做了允许配置。如果还遇到跨域或 token 异常，优先怀疑本地缓存、旧 token 和错误的请求地址，而不是先怀疑整个权限体系写错了。

如果本机同时开着 Web 端和移动端，还要特别留意它们是不是都连到了同一个后端地址。有时候问题不是跨域规则本身，而是一个页面还在请求 `localhost`，另一个页面已经改成了 `127.0.0.1` 或其他端口，结果看起来像权限或跨域异常，实际上只是联调地址没有统一。

### 7.5 RAGFlow 或模型服务不可用

这类问题不一定会把整个系统拖死。结构化数据查询、首页、工单、派工和移动端主流程通常还能继续跑；受影响更明显的是文档解析、知识检索、碳小能、运小维、维小修、多模态分析和部分 AI 审批能力。所以排查时要先区分，是“整套系统都不行”，还是“AI 辅助层失效了”。

这类分层排查思路很重要。只要能先判断是基础设施问题、数据问题、前端问题还是 AI 服务问题，排查速度会快很多。最怕的是一开始就把所有模块混在一起检查，最后花了很多时间却没有缩小问题范围。

### 8.2 默认端口

后端默认端口是 `8000`，Web 管理端默认是 `5173`，移动端 H5 常见是 `5174`，Redis 是 `6379`。RAGFlow 的本地部署地址常见是 `9380`，但这一项还是以实际部署结果为准。

这些端口信息看起来基础，但在现场联调和答辩准备里非常实用。提前把它们写在部署记录或演示清单里，能少掉很多“到底访问哪个地址”的低级错误，尤其是在需要频繁切换 Web、移动端和后端健康检查时。

### 8.3 关键环境变量

最重要的环境变量包括 `DATABASE_URL`、`SYNC_DATABASE_URL`、`REDIS_URL`、`LLM_API_KEY` 或 `DASHSCOPE_API_KEY`、`RAGFLOW_API_URL`、`RAGFLOW_API_KEY`、`RAGFLOW_DATASET_ID`、`DATA_TIME_START` 和 `DATA_TIME_END`。前面几项决定系统能不能连上基础设施，后面两项决定默认演示窗口。

### 8.4 角色和权限说明

管理员更适合做全局查看和权限维护，运维经理负责审阅、派工和执行跟踪，维修人员负责现场执行。当前系统的设计是让不同角色各管一段流程，而不是所有角色都能做所有动作。这样一方面更符合真实业务，也让状态流转更容易解释。

如果要把这部分讲得更落地，可以直接结合演示账号理解。像 `test1` 这类管理侧账号适合演示首页、数据中心、工单审阅和派工；`ops_hvac_01` 这类维修账号则更适合演示接单、到场、处理、维小修和反馈。角色一旦和实际页面对应起来，权限边界就不再是抽象概念。

### 8.5 工单状态说明

工单主状态主线是：

`pending_review -> pending_dispatch -> dispatched -> completed / false_alarm / escalated -> closed`

这条线描述的是“一张工单整体走到了哪里”。而派工执行状态主线是：

`pending_accept -> accepted -> arrived -> processing -> waiting_support(可选) -> completed`

这条线描述的是“现场任务推进到了哪里”。答辩时如果要讲状态，一定把这两层分开讲，评委更容易跟上。
