# 工单智能问询与运营洞察接口设计方案

## 0. 当前实现状态

截至 2026-04-08，已完成只读一期：

- `GET /api/work-order-insights/metrics`：返回全局工单状态、派工 SLA、维修人员负载、楼宇热点、平均执行时长和关注清单。
- `POST /api/work-order-insights/query`：先做确定性关键词意图识别，再基于同一份 metrics 返回只读中文摘要；当前不调用 LLM、不写数据库。
- 权限边界：仅 `admin / manager` 可访问跨工单运营洞察，`ops` 暂不开放全局统计。

仍未完成：

- 接入 LLM 的自然语言解释层。
- 单张工单 `insight-context` 别名接口。
- 按日期、班组、人员、楼宇等维度的参数化统计查询。

## 1. 定位

本能力不是“AI 审批”或“AI 审查”，而是面向运维人员的只读问询与运营洞察助手。

它的核心价值是让用户低成本理解工单过程，例如：

- 这张工单是谁接的？
- 中间有没有改派、协同、催办？
- 这张工单现在卡在哪一步？
- 今天有哪些工单超时？
- 本周谁接单最多？
- 哪个班组本周待关闭最多？
- 哪些工单发生过协同或接管？

一句话：它帮助用户“问工单、看概况、做统计”，不替用户执行派工动作。

## 2. 强边界

该能力必须保持只读边界：

- 不允许 AI 直接派工。
- 不允许 AI 直接改派。
- 不允许 AI 直接关闭工单。
- 不允许 AI 直接驳回工单。
- 不允许 AI 直接修改维修员画像、班组、技能或负载上限。
- 如果 AI 给出建议，只能是“建议管理员关注/建议查看/建议人工处理”，不能自动执行。

所有状态变更仍然必须走现有业务按钮、系统规则或后续明确授权的自动派工服务。

## 3. 和现有 review-context 的关系

当前已经存在：

```text
GET /api/work-orders/{ticket_id}/review-context
```

这个接口虽然技术名叫 `review-context`，但后续产品语义应理解为：

```text
单张工单智能问询上下文
```

它负责把一张工单的结构化事实整理出来，包括：

- 工单基础信息
- 当前派工
- 历史派工
- 派工事件流
- 审计日志
- 工单大厅事项与申请
- 异常证据
- 风险标记
- 规则生成的上下文摘要

后续可以保留该接口作为内部上下文服务，也可以新增别名接口：

```text
GET /api/work-orders/{ticket_id}/insight-context
```

但不建议直接把大模型调用塞进这个上下文接口。

## 4. 设计分层

建议拆成两层。

### 4.1 事实层

事实层只用确定性查询和业务服务取数，不让大模型猜数据。

事实层可以回答：

- 某张工单的当前状态是什么？
- 当前责任人是谁？
- 派工历史有几次？
- 是否发生过拒单、改派、接管、协同？
- 某个时间范围内谁接单最多？
- 某个班组本周完成了多少单？
- 哪些工单超时未关闭？

事实层的数据来源包括：

- `work_orders`
- `dispatch_tasks`
- `dispatch_events`
- `work_order_audit_log`
- `dispatch_hall_entries`
- `dispatch_hall_applications`
- `anomaly_incidents`
- `worker_profiles`
- `worker_teams`

### 4.2 表达层

表达层由 AI 负责把事实层结果解释成自然语言。

AI 可以做：

- 总结过程
- 解释状态
- 提炼异常点
- 做运营统计解读
- 给出人工关注建议
- 生成后续追问建议

AI 不可以做：

- 编造缺失数据
- 用未经查询的事实下结论
- 直接触发状态变更
- 把建议伪装成系统已执行动作

## 5. 推荐接口规划

### 5.1 单张工单上下文

已实现：

```text
GET /api/work-orders/{ticket_id}/review-context
```

未来可新增语义更准确的别名：

```text
GET /api/work-orders/{ticket_id}/insight-context
```

这类接口只返回上下文，不调用 AI。

### 5.2 运营指标查询

已新增确定性统计接口：

```text
GET /api/work-order-insights/metrics
```

后续建议参数：

```text
date_from=2026-04-01
date_to=2026-04-07
group_by=worker|team|status|building
metric=assigned|completed|overdue|reassigned|support_requested
```

典型用途：

- 本周谁接单最多？
- 本周哪个班组处理工单最多？
- 今天有哪些超时工单？
- 本周发生过几次改派？

### 5.3 自然语言问询

已新增只读确定性问询接口：

```text
POST /api/work-order-insights/query
```

请求示例：

```json
{
  "question": "本周谁接单最多？",
  "scope": {
    "date_from": "2026-04-01",
    "date_to": "2026-04-07"
  },
  "include_evidence": true
}
```

单张工单问询示例：

```json
{
  "question": "这张工单中间为什么改派？",
  "ticket_id": "WO-20260328-010",
  "include_evidence": true
}
```

响应建议：

```json
{
  "answer_type": "work_order_summary|operations_metric|mixed",
  "answer": "本周 ops_controls_01 接单最多，共 12 单，其中 3 单发生过超时。",
  "facts": [],
  "metrics": {},
  "evidence_refs": [],
  "limitations": [],
  "suggested_followups": [
    "是否查看 ops_controls_01 本周超时工单？"
  ]
}
```

## 6. 查询路由建议

自然语言问询进入后端后，建议先做意图分类，再选择事实查询路径。

建议意图类型：

- `single_work_order_summary`：单张工单概况。
- `single_work_order_timeline_question`：单张工单过程问答。
- `operations_metric`：跨工单运营统计。
- `worker_performance`：维修员维度统计。
- `team_performance`：班组维度统计。
- `overdue_analysis`：超时工单分析。
- `support_takeover_analysis`：协同/接管分析。

示例：

```text
问题：这张工单是谁接了？
路径：ticket_id -> insight-context -> AI 总结

问题：本周谁接单最多？
路径：metrics(group_by=worker, metric=assigned) -> AI 解读

问题：今天有哪些超时工单？
路径：metrics(metric=overdue) + 工单列表摘要 -> AI 解读
```

## 7. 证据引用

AI 返回结果必须能引用证据，避免“听起来像真的”但没有数据依据。

建议证据来源格式：

```text
work_order.status
current_dispatch.assigned_to_name
dispatch_tasks[1].dispatch_status
dispatch_events[3].event_type
audit_logs[2].action
hall_entries[0].entry_type
metrics.worker_rank[0]
```

如果数据不足，AI 应明确说明：

```text
当前上下文缺少早期审计日志，无法确认更早历史责任人。
```

## 8. 权限边界

建议权限：

- `admin` / `manager`：可查询全局工单和运营统计。
- `ops`：只能查询派给自己的工单，跨人员统计默认不可见。
- 后续如果开放班组长角色，可以允许查询本班组范围。

对于自然语言问询接口，必须先做权限过滤，再把结果交给 AI。

不要把用户无权访问的数据放进 prompt。

## 9. 推荐落地顺序

建议分四步落地。

### 第一步：已有能力固化

已完成：

- `GET /api/work-orders/{ticket_id}/review-context`
- `scripts/show_work_order_review_context.py`
- 单张工单上下文文档

### 第二步：补确定性运营统计接口

先不接 AI，先补：

```text
GET /api/work-order-insights/metrics
```

用于稳定回答“本周谁接单最多”“今天哪些工单超时”这类事实问题。

### 第三步：接自然语言问询接口

新增：

```text
POST /api/work-order-insights/query
```

当前该接口先做关键词意图分类和事实查询，直接返回规则生成的中文摘要；后续再把结构化事实交给 AI 生成更自然的解释。

### 第四步：接前端入口

后续可以接到现有 AI / Agent 面板，让运维人员直接问：

```text
帮我看一下 WO-20260328-010 的处理过程。
本周谁接单最多？
今天有哪些超时工单需要关注？
```

前端只展示回答、证据和建议追问，不展示任何“直接改状态”的 AI 按钮。

## 10. 命名建议

产品侧建议使用：

- `工单智能问询`
- `工单运营洞察`
- `工单概况助手`

不建议使用：

- `AI 审查`
- `AI 审批`
- `AI 裁决`

原因是这些词容易让用户误解为 AI 可以判断并修改工单状态。
