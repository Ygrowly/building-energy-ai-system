# 【文档 3】数据库与存储架构设计（原生 PG 高阶优化版）
**核心议题：**

1. **架构权衡 (Trade-off)**：在受限环境下，如何利用原生 PostgreSQL 逼近专业时序数据库的性能？
2. **物数分离设计**：关系表存“物”（静态），时序表存“数”（动态）。
3. **性能三大法宝**：复合索引、物化视图预计算、ENUM 存储优化。
4. **落地实操**：核心业务表与聚合视图的结构设计详解。
5. **后续演进规划 (Future Extension)**：构建可信 AI 的基石 —— AI 决策审计表设计。

---

这是一个非常关键的技术选型问题。我们在设计中展现了**“工程智慧”**：不依赖特定环境的高级插件（如 TimescaleDB），而是通过原生数据库的高阶特性组合，实现了一套高内聚、低耦合、高性能的存储方案。

**结论先行**：  
现阶段我们采用 **“原生 PostgreSQL 极限优化（索引+物化视图） + 非结构化知识归 RAGFlow”** 的双引擎架构，确保底层能源数据的极致纯粹与极速响应。

---

## 1. 架构权衡：为何放弃插件，回归“纯血” PostgreSQL？
**痛点**：在部分封闭环境或竞赛平台中，无法随意安装 TimescaleDB 等第三方插件。如果直接对百万级时序数据进行 `GROUP BY` 全表扫描，前端图表和大模型都将面临几十秒的超时崩溃。

**教科书级的优化策略 (The Engineering Wisdom)**：  
我们没有退缩到低效的全表扫描，而是采用了原生 PostgreSQL 的最佳实践组合拳：

+ **统一 SQL 接口**：坚守 PostgreSQL，确保 Data Agent 的 Text-to-SQL 准确率最高（防止大模型搞混不同的数据库方言）。
+ **极限性能榨取**：通过精巧的 `(building_id, "timestamp" DESC)` **复合索引**解决实时查询，通过 **物化视图 (Materialized View)** 解决长周期聚合查询。

---

## 2. 核心设计：“物数分离”与性能三大法宝
### 法宝一：关系与时序的严格解耦 (物数分离)
+ **存“物”表 (**`buildings`**)**：作为“资产身份证”，存储建筑面积、设备 ID 等静态元数据，并在 `building_type` 上建立索引。
+ **存“数”表 (**`energy_data`**)**：作为核心日志，遵循时序最佳实践：**无外键关联**（避免写入锁等待，通过应用层保证一致性），并严格使用 `TIMESTAMPTZ` 记录带时区的时间戳。

### 法宝二：“性能顶梁柱” —— 复合索引策略
+ **复合索引 (**`building_id`**, **`"timestamp" DESC`**)**：这是我们方案的性能引擎。它将同一栋楼的数据在物理上聚合在一起，并按时间倒序排列。当 Agent 查询“某栋楼最近24小时数据”或获取“最新设备状态”时，数据库只需在索引头部进行极小范围扫描，**耗时低至亚毫秒级**，完美避免了全表扫描的灾难。

### 法宝三：“手动挡”的预聚合 —— 物化视图加速
+ **痛点**：前端大屏需要展示月度、年度的每日能耗趋势。
+ **破局**：我们创造性地使用 PostgreSQL 的 **物化视图 (**`daily_energy_summary`**)**。将按天汇总的数据（SUM, AVG, MAX）作为“数据快照”预先计算好。大模型（Data Agent）和前端只需要查询这张极小的视图，查询时间从秒级直接降维到毫秒级，实现了“以空间换时间”。
+ **平滑刷新**：配合 `REFRESH MATERIALIZED VIEW CONCURRENTLY` 关键字，后台定时刷新数据时**不会锁表**，前端读取依然丝滑。

## 3. 落地实操：数据库表结构设计详解
我们坚持“最小化原则”，现阶段用最精简的表结构支撑复杂的建筑能耗业务，保持核心业务库的纯粹性。数据库由一张关系型表、一张时序数据表和一个物化视图构成。

### A. 基础信息表 (Relational) - `buildings`
+ **定位**：数字孪生世界的“资产身份证”。

```sql
CREATE TABLE buildings (
    building_id TEXT PRIMARY KEY,   -- 建筑唯一ID（如 "Education"）
    building_type TEXT,             -- 建筑类型
    meter_device_id TEXT UNIQUE NOT NULL, -- 监测设备ID（如 "M-EDU-001"）
    sqm REAL                        -- 建筑面积
);
-- 索引策略：加速按建筑类型筛选的场景
CREATE INDEX idx_buildings_type ON buildings(building_type);
```

### B. 能耗数据表 (Time-Series) - `energy_data`
+ **定位**：系统的“核心数据日志”，按时间顺序记录所有监测和仿真数据。

```sql
CREATE TABLE energy_data (
    "timestamp" TIMESTAMPTZ NOT NULL, -- 依然保留带时区的最佳实践
    building_id TEXT NOT NULL,        -- 逻辑关联 buildings 表 (无外键)
    electricity_kwh REAL,
    water_m3 REAL,
    hvac_energy_kwh REAL,
    hvac_supply_temp_c REAL,
    hvac_return_temp_c REAL,
    ambient_temp_c REAL,              -- 环境温度
    humidity_rh_pct REAL,
    occupancy_density_per_100sqm REAL,-- 人员密度
    operation_status operation_status_enum -- 运行状态 (枚举类型，节省存储空间)
);

-- 【核心性能优化】复合索引：按建筑聚合，按时间倒序
CREATE INDEX idx_energy_data_building_timestamp 
ON energy_data(building_id, "timestamp" DESC);
```

### C. 每日汇总物化视图 (Materialized View) - `daily_energy_summary`
+ **定位**：系统的“性能加速缓存”，专门应对大屏展示、报表生成等重计算场景。

```sql
CREATE MATERIALIZED VIEW daily_energy_summary AS
SELECT
    date_trunc('day', "timestamp") AS day,
    building_id,
    SUM(electricity_kwh) AS total_electricity_kwh,
    AVG(ambient_temp_c) AS avg_ambient_temp,
    MAX(occupancy_density_per_100sqm) AS max_occupancy
FROM energy_data
GROUP BY day, building_id;

-- 唯一索引：保证查询这个聚合视图时的极速响应
CREATE UNIQUE INDEX idx_daily_summary_day_building 
ON daily_energy_summary(day, building_id);
```

_(运维要求：此视图不自动更新，在应用层面设置后台定时任务执行 _`REFRESH MATERIALIZED VIEW CONCURRENTLY daily_energy_summary;`_ 以刷新快照。)_

## 4. 数据库安全策略 (Database Security) ——【企业级意识】
在多智能体系统中，防范 Prompt 注入导致数据泄露或损坏是重中之重：

1. **最小权限原则 (Least Privilege)**：
    - 分配给 `Data Agent` 的数据库账号仅拥有 `SELECT` 权限。绝对禁止 `DROP` , `DELETE` , `UPDATE`。从数据库层面物理阻断 AI 被恶意诱导删库的风险。
2. **Schema 白名单**：
    - 在 System Prompt 中，只把 `buildings`, `energy_data` 和 `daily_energy_summary` 这三张核心业务表的结构（Schema）暴露给 AI，系统内部的其他配置或缓存数据严禁暴露。

## 5. 后续演进规划 (Future Extension)：AI 决策审计表
**架构思考**：  
现阶段，我们将 AI 智能体的推理轨迹（Trace）和数据引用的上下文轻量级地保存在应用层内存（LangGraph State）中，以供前端渲染呈现。  
在项目的 **Phase 2（后续企业级演进）** 中，为了打破大模型落地的“黑盒效应”与建立工业级信任，我们规划了持久化的 **AI 决策审计表（Data Lineage / Audit Trail）**。考虑到业务库的纯粹性与高并发 I/O 隔离，未来该表可能会独立部署，或采用 ElasticSearch/MongoDB 进行专门存储。

**规划的数据结构蓝图**：

```sql
CREATE TABLE ai_audit_log (
    id SERIAL PRIMARY KEY,
    trace_id VARCHAR(100),       -- 关联单次 Agent 对话的 Session ID
    agent_name VARCHAR(50),      -- "Diagnose_Agent" 或 "Data_Agent"

    -- 1. 输入与推断（用于 Debug 幻觉）
    user_query TEXT,             -- 用户的原始请求
    raw_prompt TEXT,             -- 发给 LLM 的完整 Prompt（含注入的上下文）
    
    -- 2. 数据血缘与证据链（Trust Visualization）
    source_tables JSONB,         -- ["energy_data", "daily_energy_summary"]
    referenced_data_ids JSONB,   -- 关联的具体数据时间戳或 ID
    referenced_knowledge_ids JSONB, -- 关联的RAG手册分片ID
    
    -- 3. 结论与效能
    ai_conclusion TEXT,          -- 最终生成的结论或操作建议
    confidence_score DECIMAL,    -- AI 推理逻辑置信度 (0.0 - 1.0)
    execution_time FLOAT,        -- 链路执行总耗时（秒）
    token_usage INT,             -- API 调用的 Token 消耗量统计
    
    -- 4. 人机协同反馈 (RLHF 闭环)
    human_feedback BOOLEAN       -- 用户是否点赞/采纳建议，作为后续微调(SFT)的数据集
);
```

**演进意义**：这张表将作为系统的“行车记录仪”，不仅能为前端的“审计盾牌”提供持久化支撑，为事故追责提供依据，更为未来系统持续微调（Fine-tuning）积累宝贵的“高质量业务对话语料”。
