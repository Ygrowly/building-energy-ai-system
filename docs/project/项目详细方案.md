# 绿枢智控项目详细方案

## 文档说明

本文档不是新的需求设想，而是基于当前仓库中的实际代码、接口、页面、数据库模型与已有流程，对“绿枢智控”思维导图进行一次**落地回溯**。核心目标是说明：

- 我们已经做了哪些功能；
- 这些功能如何对应思维导图中的各个分支；
- 每一部分用了哪些关键技术；
- 哪些能力已经形成闭环，哪些仍属于预留或部分实现。

说明原则如下：

- 以当前仓库可见代码为准，不把纯方案描述当作“已完成”；
- 对已经具备页面、接口、服务、数据模型支撑的能力，认定为已落地；
- 对有骨架但尚未完全产品化的部分，会单独说明。

## 一、项目总体概述

“绿枢智控”围绕园区/建筑能耗管理与智慧运维，已经形成了一个较完整的三端协同系统：

- `backend/`：承担能耗数据治理、统计分析、智能问答、异常检测、预测预警、AI 审批、工单流转、派单调度、维修经验沉淀等核心业务；
- `frontend/`：承担 Web 管理端的总览大屏、查询统计、数据中心、智慧运维、工单管理与 AI 助手交互；
- `mobile/`：承担运维人员和维修人员的移动化操作，包括工单处理、抢单/协同、AI 辅助维修、反馈回写等。

从业务闭环来看，当前项目已经基本实现了下面这条主链路：

1. 能耗数据接入、清洗、导入、结构化存储；
2. 面向建筑、设备、指标的查询统计与可视化分析；
3. 基于规则与模型的异常检测、风险识别和 6/12 小时预测；
4. 由异常或预测结果自动生成事件/工单；
5. AI 对工单进行审批判断，并结合上下文事件做解释；
6. 智能派单、人工审核、共享调度大厅协同处理；
7. 维修人员在移动端接单、到场、维修、反馈，并使用 AI 进行步骤指导；
8. 维修过程经验沉淀到经验库，再反哺问答与指导能力。

这说明你的思维导图并不是停留在概念层面，而是已经在系统中形成了较强的工程化落地。

## 二、总体技术架构

### 2.1 后端技术栈

- `FastAPI`：作为主 Web 框架，承载数据接口、工单接口、AI 接口、管理接口；
- `SQLAlchemy + PostgreSQL`：负责建筑、设备、能耗数据、异常事件、工单、用户、经验库等核心数据建模与持久化；
- `Redis`：用于缓存、预热以及部分运行态优化；
- `JWT + 鉴权体系`：支撑登录、刷新令牌、用户身份与权限控制；
- `LangGraph`：用于构建智能问答工作流，把路由、数据查询、综合回答、诊断分析串成图式流程；
- `MCP 工具体系`：把能耗查询、设备状态、COP 计算、报表生成、知识检索、异常分析、预测、工单草稿生成等能力封装为 AI 可调用工具；
- `LangChain/OpenAI 兼容模型接入`：承载对话式问答、AI 审批、维修指导、经验摘要等大模型能力；
- `RAGFlow + 本地兜底检索`：用于知识库检索与领域问答；
- `pandas / openpyxl`：用于数据集解析、清洗、导入与结构分析；
- `scikit-learn / joblib`：用于 6h/12h 预测模型加载与推理；
- `SSE`：用于流式返回 AI 对话、导入进度、分析进度等长过程结果。

### 2.2 Web 端技术栈

- `Vue 3 + Vite + TypeScript`：构建 Web 管理端；
- `Pinia`：负责状态管理；
- `Vue Router`：组织首页、查询统计、数据中心、工单、运维分析等页面；
- `Axios`：负责接口通信；
- `ECharts / vue-echarts`：承载趋势图、分布图、Sankey、统计卡片等可视化；
- `html2pdf.js`：用于统计分析和 AI 汇总结果的报表导出；
- `marked`：用于 AI 返回内容、说明文本等富文本渲染；
- `SSE 流式客户端`：支持 AI “思考中”、文本、图表、证据、完成态等多事件流。

### 2.3 移动端技术栈

- `Uni-app + Vue 3 + TypeScript`：构建维修端与移动运维端；
- `Pinia`：负责用户、工单、通知等状态；
- `SSE/流式 AI 通信`：支撑移动端 AI 助手和指导对话；
- `音频转写 / TTS / 图片分析`：支撑维修场景中的多模态辅助；
- `移动化工单工作台`：适配接单、到场、支持申请、处理完成、反馈等流程。

## 四、核心技术设计

本章重点说明项目中真正支撑“能耗查询、风险识别、智慧运维、维修辅助”落地的核心技术。与传统系统仅依赖固定页面、静态报表和人工经验不同，“绿枢智控”围绕多智能体编排、工具调用、知识增强、规则与模型融合、流式交互和多模态辅助等能力，形成了一套面向建筑能源场景的智能化技术体系。这些技术并不是为了“堆砌前沿概念”，而是服务于查询统计、异常分析、预测预警、工单审批、派单调度和现场维修等具体业务目标。

### 4.1 基于 LangGraph 的多智能体协同编排技术

本项目并未采用单一问答机器人，而是构建了由 Router Agent、Data Agent 和 Diagnose Agent 组成的多智能体协同架构。系统首先由 Router Agent 对用户问题进行意图识别、实体抽取与置信度判断，再根据查询、诊断、工单等不同任务路由到对应智能体执行。对于“既要查数据，又要解释原因”的复合型问题，系统还支持 Data Agent 与 Diagnose Agent 的接力处理，从而实现从数据获取到诊断分析的连续推理。

这种图式编排方式的优势在于：系统不再让一个大模型承担全部任务，而是把“理解问题、调用工具、归纳数据、给出诊断”拆分为多个职责明确的节点，由状态机控制执行顺序与跳转条件。这样不仅增强了推理过程的稳定性，也降低了复杂问题下的回答漂移风险，使平台具备了从自然语言理解到业务执行的完整智能协作能力，是本项目智能化实现的总体中枢。

### 4.2 基于 ReAct 的智能体推理机制

在智能体执行层面，本项目采用了 ReAct（Reasoning + Acting）式工作机制。其核心思想不是让大模型直接输出最终答案，而是先根据问题形成初步判断，再主动调用查询、诊断、检索、预测等工具获取事实依据，最后在观察工具返回结果后继续推理并组织结论。Data Agent 和 Diagnose Agent 都遵循这一机制，因此系统中的 AI 并不是“空口回答”，而是“边思考、边调用、边验证”。

这一机制尤其适合建筑能源场景。因为能耗分析、异常归因和维修建议通常都依赖实时数据、设备状态、知识文档和规则结果，单靠语言模型记忆难以保证准确性。通过 ReAct 机制，系统能够把模型的语言理解能力与业务工具的确定性能力结合起来，从而提升输出结果的真实性、可追溯性和可解释性，也使 AI 更接近真正的“业务 Agent”而不是普通聊天机器人。

### 4.3 基于 MCP 的业务工具调用机制

为了避免大模型直接拼接 SQL 或脱离业务规则进行自由生成，本项目在 AI 与业务系统之间设计了 MCP 标准工具层，将能耗查询、设备状态查询、COP 计算、异常检测、预测预警、知识检索、工单草稿生成、报表生成等能力统一封装为标准工具。系统通过工具注册中心、统一调用入口和参数校验机制，使大模型从“自由回答”转变为“按规则调用业务能力”。

该机制的优势在于：一方面，MCP 工具层显著提升了系统的稳定性、可控性与可审计性；另一方面，也提高了系统的扩展能力，后续若新增分析工具、业务动作或新型 Agent，只需在工具层扩展即可，而不需要重写整条智能链路。因此，MCP 在本项目中实际上承担了“AI 与业务系统之间标准接口层”的作用，是实现查询、诊断、预测、工单与报表联动的关键技术。

### 4.4 AI 驱动的动态界面生成技术

本项目中的 AI 并不只是返回一段文字，而是能够输出结构化 Artifact，由前端动态渲染为图表卡片、诊断面板、工单卡片和报表下载组件。也就是说，系统不仅实现了“AI 会回答”，还实现了“AI 会组织结果的展示形式”。在查询统计、故障诊断和工单确认等场景下，这种生成式 UI 机制能够把文本结论、数据摘要和交互组件组合成更适合业务使用的界面结果。

这一技术的价值在于把 AI 输出从“单一文本流”升级为“结构化前端渲染指令”，增强了系统的人机协同体验。对于管理端用户而言，AI 不再只是说明问题，而是可以同时给出可视化组件和下一步操作入口；对于维修和运维场景而言，也可以更方便地展示工单草稿、诊断卡片和下载报表。这是本项目区别于普通问答系统的重要创新点之一。

### 4.5 流式可解释交互技术

在交互方式上，本项目采用基于 SSE 的流式事件驱动机制，而不是传统的一次性同步返回。系统在对话过程中会持续输出 thinking、text、artifact、done 等不同类型事件，前端和移动端则对这些事件进行专门适配，实现“边思考、边展示、边生成组件”的渐进式交互体验。这样，用户能够实时看到系统正在分析什么、输出了哪些文本、生成了哪些图表或卡片，而不必等待整个流程全部结束。

这种设计显著提升了智能交互的透明度和可解释性。对于复杂的查询分析、运维诊断和维修指导任务，用户不仅能更快获得阶段性反馈，也更容易理解系统的推理过程和输出结构。尤其在建筑能源管理这类业务问题链条较长的场景下，流式可解释交互能够有效降低等待焦虑，增强用户对 AI 结果的信任感和使用体验。

### 4.6 基于 RAGFlow 的知识增强检索技术

在智慧运维与维修指导场景中，单纯依赖通用大模型难以保证专业性和稳定性。为此，本项目引入 RAGFlow 作为知识检索引擎，将设备手册、运维规范、能耗分析资料、历史工单经验等文档转化为可检索知识，并在问答、诊断和维修指导过程中进行知识增强生成。系统在接收到专业问题后，可先进行知识检索，再将检索结果与当前工单、设备状态和异常信息结合，生成更符合领域场景的回答。

同时，为了保证系统在演示和部署环境中的鲁棒性，项目还设计了本地知识库兜底机制。当外部 RAG 服务未配置或不可用时，系统仍能依靠本地知识片段完成基础检索与回答。该技术显著提升了 AI 回答的领域相关性、专业可信度和落地可用性，是实现运维问答、标准规范查询和维修辅助的重要底座。

### 4.7 期望值基线生成模型

在异常检测和预测预警之前，系统首先需要回答一个更基础的问题，即“当前楼宇在此时此刻正常情况下应该运行到什么水平”。为了解决这一问题，本项目构建了逐小时 KPI 期望值基线生成模型，用于生成 `kpi_expected_hourly` 期望值数据。该模型不是简单取历史平均值，而是综合考虑建筑类型、运行日程、时间位置、气候影响以及 HVAC 工况等因素，对水耗、电耗、空调能耗以及供回水温度等关键指标给出额定参考值。

其中，系统在基线生成过程中还引入了建筑类型映射、日程系数调节、空调模式识别、HVAC 滞回状态机和供回水额定温度建模等逻辑，使期望值不仅具有统计意义，也具有工程语义。正因为有了这一层基线模型，后续异常检测能够判断“是否偏离正常工况”，预测预警也能够比较“未来是否会超出合理范围”。因此，期望值基线生成模型实际上是本项目异常识别和主动预警能力的共同底座。

### 4.8 基于物理规则与国标耦合的混合智能分析技术

本项目的智能分析并非完全依赖黑盒模型，而是采用“物理机理 + 国标基准 + 业务规则 + AI 解释”相结合的混合智能思路。系统在 COP 计算、额定值对比、供回水温差分析、空调根因识别等环节中，都引入了建筑能源领域的物理约束和国家标准参考值，例如 GB 相关基准、空调系统供回水额定温度、温差阈值和能耗合理范围等。这种设计保证了系统输出不仅“像 AI 的回答”，更是“符合建筑能源专业逻辑的判断”。

这种混合智能方案的价值在于，它把大模型的理解与归纳能力建立在确定性规则和工程知识之上，使系统既能保持智能交互能力，又不会偏离建筑能源赛题的专业边界。对于评审和答辩场景而言，这种“不是纯大模型、也不是纯规则，而是规则与智能融合”的表达会更贴合智慧建筑与能源管理的真实需求。

### 4.9 基于期望值基线与双阈值规则的异常检测算法

在异常识别方面，本项目采用“期望值基线 + 相对偏差阈值 + 绝对偏差阈值”的双阈值检测思路。系统首先基于期望值模型生成逐小时 KPI 基线，再将实时或历史实际值与期望值进行对比，对水耗异常、电耗超标和空调过耗等情形进行识别。相比简单的固定阈值告警，这种方法能够更好适应不同建筑、不同时间段和不同工况下的运行差异，从而降低误报率。

针对 HVAC 异常，系统还进一步设计了根因识别规则，能够区分主机效能衰退、水力失调、非预期开机等典型问题类型，使系统不仅能“发现异常”，还能够“解释异常”。由于该检测算法建立在期望值基线和物理规则基础之上，因此它既具备较强的工程可信度，又能够与 AI 诊断、工单生成和运维分析形成联动，是本项目从数据监测走向智能运维的关键环节。

### 4.10 基于多指标特征工程的 6/12 小时 KPI 预测模型

为了实现从事后响应向事前预警的转变，本项目构建了面向未来 6 小时和 12 小时的综合 KPI 预测能力。预测对象不是单一电耗，而是包括水耗、电耗、空调能耗、供水温度和回水温度在内的多项关键运行指标。模型围绕多指标联合预测进行设计，通过滞后特征、滚动统计特征、时间特征和气象特征等多维信息，构建建筑短时运行趋势预测能力。

在工程实现上，项目采用 `scikit-learn + joblib` 的方式对预测模型进行封装，并通过独立推理 Worker 进程执行模型推理，以避免主业务服务与模型依赖耦合。预测结果还会继续与期望基线进行比对，形成预测异常事件，并进一步驱动预测类工单生成。该技术使平台具备了提前发现风险、提前安排处理资源的能力，增强了系统的主动预警水平。

### 4.11 基于上下文事件推理的大模型工单审批技术

在工单流转环节，本项目引入了 AI 审批机制。系统会先查询当前建筑在异常发生时段内的上下文事件，例如加班、装修、极端天气、维护窗口等，再由大模型判断这些事件是否能够合理解释当前异常。如果异常能够被当前事件背景解释，则可驳回派单；若无法解释，则批准进入后续派单流程。

这一技术的关键价值在于，它不是简单地根据异常本身做决策，而是将“异常检测结果”与“业务场景上下文”进行联合推理，从而减少误触发工单和无效派单。同时，系统还设计了失败降级和审计日志机制，在模型调用异常时仍可保障流程继续运行，并为后续人工复核提供完整依据，从而兼顾了智能化与业务可靠性。

### 4.12 基于规则评分的智能派单与自动重派技术

在派单调度方面，项目构建了规则评分式智能派单机制。系统综合考虑维修人员的技能匹配、班组归属、楼宇覆盖范围、值班状态、当前负载、候选分差等多个因素，对候选人进行排序与推荐，并区分高置信自动派工、低置信兜底派工和进入共享调度大厅三类处理策略。这样既提高了自动化程度，也保留了复杂场景下的人工复核和协同处理空间。

此外，在工单超时、处理受阻或协同失败等场景下，系统还支持自动重派评估与改派执行。该技术体现了项目在“运维调度智能化”方面的能力，不再停留于简单的工单流转，而是进一步实现了基于规则决策的资源优化配置和流程自适应调整。

### 4.13 基于多模态大模型的现场维修辅助技术

面向移动维修端，本项目进一步引入了多模态 AI 能力。系统支持维修人员上传现场图片、语音描述和文本问题，由多模态模型完成图片理解、语音转写、语音播报和步骤指导，并结合当前工单、知识库与经验库生成维修建议卡片。相比传统静态工单系统，这种多模态交互方式更加贴近真实维修流程，能够降低一线人员对个人经验的依赖。

同时，系统还支持维修过程中的经验沉淀与回流，将现场处理记录、维修结论和经验总结持续纳入经验库，供后续相似工单复用。该技术不仅提升了单次维修效率，也增强了平台在长期运行中的知识积累能力，使系统具备“边使用、边学习、边沉淀”的持续优化特征。

## 五、系统已形成的核心业务闭环

结合当前代码实现，项目已经形成以下几个关键闭环：

### 5.1 数据闭环

- 原始数据集上传；
- 字段分析、清洗、标准化；
- 导入业务表；

### 5.2 分析闭环

- 可视化统计分析；
- AI 对话查询；
- 自动生成分析报告。

### 5.3 运维闭环

## 七、关键边界最终说法

本节直接回答项目中最容易被追问的几个关键问题。

### 7.1 异常检测是规则为主，还是规则 + 模型

最终说法：

- **异常检测是规则为主**；
- 更准确地说，是“**期望值基线 + 双阈值规则 + 空调根因规则**”；
- 当前异常检测逻辑直接来自 Notebook 中沉淀的检测规则，并不是训练型异常分类模型。

需要特别说明的边界：

- 系统会先计算 `kpi_expected_hourly` 期望值，再把实际值和期望值进行规则比较；
- 异常识别本身没有使用机器学习异常分类器；
- “模型”主要用于后面的 6/12h 预测，不应把预测模型和异常检测模型混为一谈。

### 7.2 6/12h 预测预测什么指标

最终说法：

- **6/12h 预测的是综合 KPI，而不是单一电耗**；
- 当前模型直接预测 5 项指标：
  - 水耗 `water_l`
  - 电耗 `electricity_kwh`
  - 供水温度 `sim_supply_temp_c`
  - 回水温度 `sim_return_temp_c`
  - 空调能耗 `hac_energy`

需要特别说明的边界：

- 预测结果不是直接输出 COP；
- 预测结果也不是直接输出“总负荷”；
- COP、性能判断、风险判断更多是基于这些 KPI 再做衍生分析；
- 因此正式文档里应写“综合 KPI 预测”，不要只写“电耗预测”。

### 7.3 AI 审批工单是完整可跑，还是演示流程

最终说法：

- **AI 审批工单属于完整可跑流程，不是纯演示假流程**；
- 当前已经具备工单进入 `pending_review`、AI 审批、写回审批结果、人工重审、管理员覆盖、审计日志记录等完整链路。

需要特别说明的边界：

- 若配置了 LLM 与上下文事件数据，则 AI 审批会进行真实判断；
- 若 LLM 未配置或调用失败，系统会走“降级批准（fail-open）”路径；
- 因此它是“**完整业务链路 + 可降级运行**”，而不是只做页面演示。

### 7.4 智能派单是基于规则，还是基于模型推荐

最终说法：

- **智能派单当前是基于规则 / 启发式评分，不是机器学习推荐模型**；
- 当前评分显式考虑：
  - 技能匹配
  - 班组匹配
  - 楼宇覆盖
  - 当前班次
  - 当前负载
  - 紧急任务可接能力
  - 是否开启派工

需要特别说明的边界：

- 当前已经有自动派单 dry-run、低置信兜底、共享大厅 fallback、自动重派评估；
- 但自动执行默认受 feature flag 与灰度范围控制；
- 所以正式文档最稳妥的说法是“**规则评分推荐 + 灰度自动执行**”。

### 7.5 移动端是完整可用，还是原型 / 部分页面

最终说法：

- **移动端对工单主链路是完整可用的，不是只有静态原型**；
- 当前已经具备登录、角色切换、待办/在办/大厅、工单详情、执行动作、反馈、通知、AI 辅助等真实页面和接口联动。

需要特别说明的边界：

- 移动端重点承载的是“运维工单”和“维修执行”主流程；
- 它不是 Web 全功能等价版本，不承载数据中心、复杂查询统计、后台管理的全部能力；
- 因此正式文档建议写成“**移动端已完成工单与维修闭环，Web 端承担重分析与重管理**”。

## 八、知识库、大模型与 MCP 设计说明

### 8.1 知识库资料来源

当前系统中的知识来源主要有四类：

- 设备手册、运维手册、运维规范类文档；

- 历史工单、相似工单、维修人员现场反馈；

其中：

- 维修经验库来自 `maintenance_experiences` 相关表与服务；
- 维修指导还会结合相似工单与当前工单上下文共同生成建议。

最终说法建议：

- 正式文档可以写成“知识来源覆盖设备手册、运维规范、能耗分析资料、历史工单经验和结构化维修经验库”。

### 8.2 RAGFlow 是真实接入，还是仅为方案推荐

最终说法：

- **RAGFlow 是真实接入的，不只是方案推荐**；
- 当前已实现：
  - 文档上传到 RAGFlow 数据集；
  - 文档列表查询；
  - 文档删除；
  - 文档解析状态查询；
  - 手动触发切片/解析；
  - 检索调用 `/api/v1/retrieval`。

需要特别说明的边界：

- 如果 `RAGFLOW_API_KEY` 或 `RAGFLOW_DATASET_ID` 未配置，系统会自动降级到本地知识库；
- 因此正式文档最准确的表述是“**已接入 RAGFlow，并设计本地知识兜底机制**”。

### 8.3 LLM 到底写哪家模型

最终说法建议：

- 正式文档不建议把模型厂商写死成唯一答案，而应写成“**OpenAI 兼容大模型接口 + 多模态轻量模型**”；
- 如果需要补充实现细节，可说明：
  - Web 主对话、AI 审批等后端链路默认采用 OpenAI 兼容接口，当前默认配置偏向 `DeepSeek / deepseek-chat`；
  - 维修端与运维端双端 AI 默认采用 DashScope 兼容接口，当前默认配置偏向通义模型族，如 `qwen-plus`、`qwen3-vl-flash`、`qwen3-asr-flash`。

最终推荐写法：

- “系统通过 OpenAI 兼容接口接入可切换的大模型与多模态模型，在不同场景下分别承担问答、审批、视觉理解、语音识别和语音播报任务。”

这样写最稳妥，因为它既真实，又保留了部署切换空间。

### 8.4 MCP 工具写到多细，以及为什么这样设计

正式文档建议写到“工具分组 + 代表工具 + 设计原因”这一层，不必展开到每个入参字段。

当前已封装的 MCP 工具可以概括为五类：

- 数据查询类：`query_energy_metrics`、`query_daily_energy_summary`、`compare_metric_across_buildings`、`compare_time_periods`、`list_available_buildings`
- 设备与物理分析类：`get_device_live_status`、`calculate_system_cop`、`get_building_rated_values`、`detect_energy_anomalies`
- 知识检索类：`rag_hybrid_search`、`web_search`
- 业务动作与呈现类：`render_ui_component`、`create_work_order_draft`、`generate_report`
- 预测类：`building_kpi_forecast_6h_12h`、`building_kpi_forecast_from_features`

为什么这样设计：

- 让 AI 通过标准工具访问业务能力，而不是直接拼 SQL；
- 通过 Pydantic 做参数校验，提高稳定性和可审计性；
- 让“查询、分析、预测、工单、报表、UI 渲染”都能成为统一工具能力；
- 便于 LangGraph 在流程中组合调用，形成稳定的业务 Agent；
- 便于后续新增工具，而不必重写整条 Agent 链路。

最终说法建议：

- 正式文档里写“**MCP 作为 AI 与业务系统之间的标准工具层**”，这是最有解释力的表述。

## 九、系统角色与权限边界

### 9.1 当前代码中的实际角色

当前代码中 `User.role` 的角色枚举为：

- `admin`：系统管理员
- `manager`：运维经理
- `ops`：维修人员

### 9.2 正式文档建议采用的角色口径

如果面向答辩或正式文档，建议把角色定义成下面这四类：

- **系统管理员**：负责系统配置、账号管理、监督与覆盖关键决策；
- **能源管理人员**：负责能耗查询、统计分析、知识维护、风险研判、报表输出；
- **运维调度人员**：负责工单审阅、派单、调度大厅协同、运行监控；
- **维修人员**：负责接单、到场、处理、反馈、经验沉淀。

需要特别说明的边界：

- `admin` 具备更高层级的监督和覆盖权限；
- `resident` 在当前项目主流程中不是重点业务角色，可以在正式文档中弱化。

### 9.3 各角色权限边界的最终说法

系统管理员：

- 管理系统运行与账号；
- 查看全部工单与调度过程；
- 对 AI 审批结果进行重审、覆盖、关闭；
- 具备运维经理的全部核心权限。

能源管理人员 / 运维调度人员：

- 使用 AI 查询、报表导出、知识库与经验库；
- 审阅工单、查看候选人、执行派单、查看调度大厅与工单洞察；
- 管理维修人员画像与排班相关信息。

维修人员：

- 在移动端查看待办与在办工单；
- 执行接单、到场、开始处理、请求协同、恢复处理、提交结果；
- 使用维小修进行辅助维修、图片分析、语音交互；
- 提交维修经验与现场反馈。

最终说法建议：

- 正式文档里可以保留四类业务角色；
- 但若被追问代码实现，应说明“当前实现层面主要是 `admin / manager / ops / resident`，其中 manager 承担能源管理与调度职责”。

## 十、最终工单业务流程

正式文档中建议采用下面这条流程，和当前系统实现最一致：

1. **异常发现 / 预测预警**
   - 来自异常检测或 6/12h 预测。
2. **事件生成**
   - 写入异常事件或预测异常事件。
3. **工单生成**
   - 根据异常或预测结果生成工单，来源可为 `auto_detect`、`prediction` 或人工创建。
4. **AI 审批**
   - 工单先进入 `pending_review`；
   - AI 结合上下文事件进行审批；
   - 如模型异常，可走降级批准；
   - 管理员可手动重审或覆盖。
5. **待派单**
   - 审批通过后进入 `pending_dispatch`。
6. **派单 / 自动派单 / 大厅兜底**
   - 可手动派单；
   - 可辅助推荐与批量推荐；
   - 可按灰度规则自动派单；
   - 若无法明确责任人，可进入共享调度大厅。
7. **接单执行**
   - 维修人员接单、到场、开始处理；
   - 必要时发起协同支持。
8. **维修反馈**
   - 维修人员提交“已修复 / 误报 / 升级处理”等结果；
   - 写回工单状态和审计日志。
9. **人工确认与关闭**
   - 管理侧可确认关闭、驳回、升级或覆盖部分决策。
10. **经验沉淀**
    - 工单经验、现场备注、结构化维修经验回流知识库/经验库。

需要特别强调的一个边界：

- “人工复核”在当前系统里是**关键监督节点**，但不是所有工单都必须经过人工后才允许派单；
- 当前实现更准确的说法是“**AI 审批为主，人工可重审 / 覆盖 / 复核自动派工结果**”。

## 十一、总结

从当前仓库实现来看，“绿枢智控”已经完成了从**数据接入、查询统计、AI 问答、异常检测、预测预警、AI 审批、智能派单、移动维修、经验沉淀**的一整套智慧运维链路。

如果用一句话概括本项目当前的成熟度，最准确的表述是：

- **数据处理与查询统计属于已完成模块；**
- **智慧运维主链路已完成，但全自动执行、严格实时化和仿真平台化仍应按演示级或规划中表述；**
- **知识库、大模型、MCP 和移动维修端是本项目最有辨识度的亮点能力。**

也就是说，思维导图上的大部分内容已经不只是“计划要做”，而是已经以代码、接口、页面和业务流程的形式落到了系统里。当前最值得强调的特点有三点：

- 第一，系统不是单一看板，而是打通了数据、分析、工单和维修执行；
- 第二，AI 能力不是装饰，而是深度嵌入查询、审批、派单、指导与经验沉淀；
- 第三，项目已经形成了“发现问题 -> 判断问题 -> 生成工单 -> 派单处理 -> 经验回流”的闭环基础。

后续如果继续迭代，最适合增强的方向主要有两类：

- 把数据仿真/自动造数能力产品化；
- 把异常监测从定时任务进一步升级为更高频、更实时的流式监测体系。

但就当前仓库而言，这个项目已经能够较完整地支撑你的思维导图主体内容，并且具备了较强的展示、答辩和继续开发基础。
