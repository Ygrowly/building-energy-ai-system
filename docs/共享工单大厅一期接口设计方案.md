# 共享工单大厅一期接口设计方案

## 1. 目标

基于 [共享工单大厅与我的工单边界设计方案](./共享工单大厅与我的工单边界设计方案.md)，一期先不做完整的共享调度生态，只落最必要的两类共享任务：

1. `未指派协同`
2. `超时待接管`

一期目标是先打通“共享暴露 -> 人员申请 -> 管理端确认 -> 转正式责任”的最小闭环。

---

## 2. 一期范围

### 2.1 纳入共享工单大厅的任务

一期仅纳入以下两类：

#### A. 未指派协同

场景：

- 当前责任人发起协同请求
- 尚未明确协同责任人

大厅动作：

- `我可协同`

流转结果：

- 管理员确认后，协同任务进入指定维修员“我的工单”

#### B. 超时待接管

场景：

- 当前责任人接单超时
- 到场超时
- 持续处理超时且无明确说明

大厅动作：

- `申请接管`

流转结果：

- 管理员确认后，生成新的正式派工/改派关系

### 2.2 一期明确不做

以下内容建议留到后续阶段：

1. 公开认领
2. 系统推荐给我
3. 自动委派
4. 自动重派
5. 大厅内直接抢单

---

## 3. 推荐对象设计

一期建议新增独立对象：

- `dispatch_hall_entry`

不要把共享暴露语义直接硬塞进 `dispatch_task`。

### 3.1 建议字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | uuid | 主键 |
| `work_order_id` | uuid | 关联工单 |
| `incident_id` | uuid | 关联 incident |
| `source_dispatch_id` | uuid nullable | 来源派工任务 |
| `entry_type` | text | `support_request` / `takeover_candidate` |
| `status` | text | `open` / `assigned` / `closed` / `expired` |
| `visibility_scope` | text | `team_only` / `skill_pool` / `recommended_users` / `all_ops` |
| `target_team_ids_json` | json nullable | 可见班组 |
| `target_skill_tags_json` | json nullable | 技能标签 |
| `target_user_ids_json` | json nullable | 定向可见用户 |
| `reason` | text nullable | 进入大厅原因 |
| `support_reason` | text nullable | 协同原因 |
| `sla_stage` | text nullable | `accept` / `arrive` / `finish` |
| `overdue_level` | text nullable | `warning` / `overdue` / `severe` |
| `allow_direct_claim` | bool | 一期建议固定为 `false` |
| `created_by` | uuid nullable | 发起人 |
| `created_at` | timestamptz | 创建时间 |
| `expired_at` | timestamptz nullable | 失效时间 |
| `assigned_at` | timestamptz nullable | 被确认进入正式责任池的时间 |
| `closed_at` | timestamptz nullable | 关闭时间 |

### 3.2 推荐索引

- `(status, entry_type, created_at desc)`
- `(incident_id, status)`
- `(work_order_id, status)`
- `(source_dispatch_id)`

---

## 4. 一期权限模型

### 4.1 维修员可见范围

维修员默认不能看所有大厅条目。

一期建议仅允许查看以下命中的条目：

1. 自己所在班组命中 `target_team_ids`
2. 自己技能命中 `target_skill_tags`
3. 自己在 `target_user_ids` 中
4. `visibility_scope = all_ops`

### 4.2 维修员允许动作

#### 对 `support_request`

- `apply_support`

#### 对 `takeover_candidate`

- `apply_takeover`

维修员一期不允许：

- 直接改派
- 直接接管
- 关闭大厅条目

### 4.3 管理员允许动作

- 查看全部大厅条目
- 查看申请记录
- 确认协同分配
- 确认接管
- 驳回申请
- 关闭大厅条目

---

## 5. 一期需要的配套对象

一期建议新增申请对象：

- `dispatch_hall_application`

### 5.1 建议字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | uuid | 主键 |
| `hall_entry_id` | uuid | 对应大厅条目 |
| `applicant_user_id` | uuid | 申请人 |
| `application_type` | text | `support` / `takeover` |
| `status` | text | `pending` / `approved` / `rejected` / `withdrawn` |
| `note` | text nullable | 申请说明 |
| `created_at` | timestamptz | 创建时间 |
| `handled_by` | uuid nullable | 审批人 |
| `handled_at` | timestamptz nullable | 审批时间 |
| `handle_note` | text nullable | 审批说明 |

---

## 6. 一期接口建议

### 6.1 查询共享工单大厅

`GET /api/dispatch-hall`

#### 查询参数

- `entry_type`
- `status`
- `building_id`
- `priority`
- `team_id`
- `mine_only`
- `page`
- `page_size`

#### 返回重点字段

- 大厅条目基础信息
- 当前主责任人
- 当前卡点
- 进入大厅原因
- 是否命中我
- 是否已申请
- 可执行动作

---

### 6.2 查询单条大厅详情

`GET /api/dispatch-hall/{entry_id}`

#### 返回重点字段

- 工单摘要
- 当前责任人
- 派工历史摘要
- SLA 阶段
- 协同/超时原因
- 已有申请列表
- 建议动作

---

### 6.3 维修员申请协同

`POST /api/dispatch-hall/{entry_id}/apply-support`

#### 请求体

```json
{
  "note": "我可协同处理弱电联动部分"
}
```

#### 结果

- 新增一条 `dispatch_hall_application`
- 条目状态仍保持 `open`
- 等待管理员确认

---

### 6.4 维修员申请接管

`POST /api/dispatch-hall/{entry_id}/apply-takeover`

#### 请求体

```json
{
  "note": "我当前空闲，可立即接手处理"
}
```

#### 结果

- 新增 `takeover` 类型申请
- 条目状态保持 `open`
- 等待管理员确认

---

### 6.5 管理员确认协同分配

`POST /api/dispatch-hall/{entry_id}/assign-support`

#### 请求体

```json
{
  "application_id": "xxx",
  "assigned_to": "user_id",
  "note": "确认由弱电班李晨协同处理"
}
```

#### 结果

- 关闭该申请
- 大厅条目标记为 `assigned`
- 创建正式协同任务
- 该协同任务进入被分配维修员“我的工单”
- 被分配维修员可 `接受 / 拒绝`

---

### 6.6 管理员确认接管

`POST /api/dispatch-hall/{entry_id}/assign-takeover`

#### 请求体

```json
{
  "application_id": "xxx",
  "assigned_to": "user_id",
  "reason": "原责任人长时间未到场，确认由他人接管"
}
```

#### 结果

- 当前共享申请转正式
- 创建新的正式派工/改派关系
- 更新 `current_dispatch`
- 工单进入新责任人“我的工单”
- 大厅条目转为 `assigned` 或 `closed`

---

### 6.7 管理员驳回申请

`POST /api/dispatch-hall/applications/{application_id}/reject`

#### 结果

- 申请状态改为 `rejected`
- 条目继续保持 `open`

---

### 6.8 管理员关闭大厅条目

`POST /api/dispatch-hall/{entry_id}/close`

#### 场景

- 已无共享必要
- 已完成正式分配
- 工单状态变化，不再适合留在大厅

---

## 7. 一期状态流转

### 7.1 未指派协同

```text
主责任人申请协同
  -> 创建 hall_entry(entry_type=support_request, status=open)
  -> 维修员申请协同
  -> 管理员确认
  -> 创建正式协同任务
  -> 进入被分配维修员“我的工单”
  -> hall_entry 关闭
```

### 7.2 超时待接管

```text
SLA 规则触发“待接管”
  -> 创建 hall_entry(entry_type=takeover_candidate, status=open)
  -> 维修员申请接管
  -> 管理员确认
  -> 正式改派/接管
  -> 更新 current_dispatch
  -> hall_entry 关闭
```

---

## 8. 与“我的工单”的关系

一期必须强制遵守下面两条：

1. `共享大厅 != 我的工单`
2. `进入我的工单` 必须经过一次正式分配确认

特别是协同任务：

- 未指派协同：在大厅
- 已指派协同：进入“我的工单”

这条边界不能模糊。

---

## 9. 一期前端落地建议

### 9.1 维修端

一期不建议立刻把共享工单大厅做成复杂页面。

建议先完成：

1. 当前“工单”页正名为“我的工单”
2. 单独预留“共享工单大厅”入口
3. 共享大厅先只做列表 + 申请动作

### 9.2 管理端

管理端一期先不新开大页面，先挂在现有派工中心/执行跟踪页内：

- 可看到大厅条目
- 可看到申请列表
- 可执行确认协同/确认接管

---

## 10. 后续扩展方向

一期跑稳后，再考虑：

1. `公开认领`
2. `系统推荐给我`
3. `系统自动确认协同`
4. `系统自动确认接管`
5. `共享大厅的评分和排序模型`

---

## 11. 最终结论

共享工单大厅一期的最小闭环建议是：

- 只做 `未指派协同` 和 `超时待接管`
- 工人只能申请，不能直接抢
- 管理员确认后，才进入维修员“我的工单”

这样可以先把大厅和正式责任池彻底分开，再逐步扩展到更复杂的共享与自动调度场景。
